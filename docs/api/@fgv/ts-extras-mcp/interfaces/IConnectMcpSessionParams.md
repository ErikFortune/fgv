# Interface: IConnectMcpSessionParams

Parameters for [connectMcpSession](../functions/connectMcpSession.md).

## Properties

| Property | Modifier | Type | Description |
| ------ | ------ | ------ | ------ |
| <a id="property-clientname"></a> `clientName?` | `readonly` | `string` | Client name advertised to the server during the initialize handshake. Default `'@fgv/ts-extras-mcp'`. |
| <a id="property-clientversion"></a> `clientVersion?` | `readonly` | `string` | Client version advertised to the server. Default the package version. |
| <a id="property-logger"></a> `logger?` | `readonly` | [`ILogger`](https://github.com/ErikFortune/fgv/tree/main/libraries/ts-utils/docs) | Optional logger for connection diagnostics. |
| <a id="property-onclose"></a> `onClose?` | `readonly` | () => `void` \| `Promise`\<`void`\> | Called once when the session's connection closes, for any reason: the server process exited, the transport failed, or [closeMcpSession](../functions/closeMcpSession.md) was called. It is never called for a session whose connect failed, and never more than once. **Remarks** This is an observation, not a policy: the package never reconnects. A consumer that pools sessions uses it to retire a dead session before its next call rather than after. A call made on a closed session fails with the `'not-connected'` [McpFailureReason](../type-aliases/McpFailureReason.md). The callback runs synchronously inside the SDK's close handling. A throw from it is caught (and logged to `logger`, when one is supplied) so that it cannot stop the SDK from failing the session's in-flight requests. It may be `async`: a promise it returns is not awaited (the SDK fails the in-flight requests straight after), but a rejection of that promise is caught and logged the same way, never left as an unhandled rejection. A Streamable-HTTP session has no connection to lose between requests, so a server that restarted is not observed here; the next call reports it, as `'session-expired'` when the server answers HTTP 404 for the stale session id. |
| <a id="property-ontoolschanged"></a> `onToolsChanged?` | `readonly` | () => `void` \| `Promise`\<`void`\> | Called when the server sends `notifications/tools/list_changed`: its tool catalog has changed since the consumer last listed it. **Remarks** An observation only: the package does not re-list. Call [listMcpTools](../functions/listMcpTools.md) (or [adaptMcpTools](../functions/adaptMcpTools.md)) when it fires. Once the session is returned it fires once per notification, and never once [closeMcpSession](../functions/closeMcpSession.md) has been called (an HTTP close can stay open for up to two seconds while the server's session is terminated), after the connection has closed, or for a session whose connect failed. Any notifications that arrive while the connect is still settling are delivered as one call (a single re-list covers them all), shortly after [connectMcpSession](../functions/connectMcpSession.md) has returned the session, so the callback can always use the handle. Whether a server sends the notification is its choice; one that advertises `capabilities.tools.listChanged` says it will. The callback is contained exactly as `onClose` is: a throw, or a rejection of the promise an `async` callback returns, is caught and logged to `logger`, never propagated and never left unhandled. |
| <a id="property-signal"></a> `signal?` | `readonly` | `AbortSignal` | Aborts the connect. An abort at any point before the connect settles — while the transport starts, while `initialize` is in flight, or while the SDK sends `notifications/initialized` — fails the connect with the `'aborted'` [McpFailureReason](../type-aliases/McpFailureReason.md) and starts closing the transport, so an aborted connect never hands back a live session. As with a timeout, the failure does not wait for the close to finish. |
| <a id="property-timeoutms"></a> `timeoutMs?` | `readonly` | `number` | Timeout in milliseconds for the whole connect: starting the transport, the `initialize` request, and sending `notifications/initialized`. Defaults to the SDK's 60 000. Expiry fails the connect with the `'timeout'` [McpFailureReason](../type-aliases/McpFailureReason.md) and starts closing the transport; the failure is returned without waiting for that close, so teardown (a stdio child's exit, a slow custom `close()`) can finish after the connect has returned. Must be a positive, finite number no greater than 2³¹−1 (`setTimeout`'s limit); anything else fails with `'invalid-options'`. |
| <a id="property-transport"></a> `transport` | `readonly` | [`IMcpTransport`](IMcpTransport.md) | A transport produced by [createStdioTransport](../functions/createStdioTransport.md), [createHttpTransport](../functions/createHttpTransport.md) or [createCustomTransport](../functions/createCustomTransport.md). |
