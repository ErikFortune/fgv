# Interface: IAdaptMcpToolsOptions

Options for [adaptMcpTools](../functions/adaptMcpTools.md).

## Properties

| Property | Modifier | Type | Description |
| ------ | ------ | ------ | ------ |
| <a id="property-discovery"></a> `discovery?` | `readonly` | [`IListMcpToolsOptions`](IListMcpToolsOptions.md) | Options for the tool discovery `adaptMcpTools` runs — passed to [listMcpTools](../functions/listMcpTools.md) as given, including its bounds over the paged listing ([IListMcpToolsOptions.maxPages](IListMcpToolsOptions.md#property-maxpages), [IListMcpToolsOptions.maxTotalMs](IListMcpToolsOptions.md#property-maxtotalms)) and each page's `timeoutMs` and `signal`. A discovery failure, a bound exceeded included, fails the whole adaptation with its [McpFailureReason](../type-aliases/McpFailureReason.md). When omitted, discovery is unbounded, as [listMcpTools](../functions/listMcpTools.md) is. |
| <a id="property-logger"></a> `logger?` | `readonly` | [`ILogger`](https://github.com/ErikFortune/fgv/tree/main/libraries/ts-utils/docs) | Logger for the NOISY per-tool skip warnings. When a tool is skipped, a `warning` is emitted including the tool name, the JSON-pointer reason, and the raw failing schema. When omitted, skips are still surfaced structurally on [IAdaptMcpToolsResult.skipped](IAdaptMcpToolsResult.md#property-skipped). |
| <a id="property-patternvalidator"></a> `patternValidator?` | `readonly` | [`SchemaPatternValidator`](https://github.com/ErikFortune/fgv/tree/main/libraries/ts-json-base/docs) | Compiles the `pattern` keyword of a server's tool schemas; passed to `JsonSchema.fromJson`. **Remarks** Without it, a tool whose schema uses `pattern` is skipped, because this package never compiles a server-supplied regular expression: a backtracking `RegExp` built from one is a ReDoS vector on every tool call, and a synchronous match cannot be timed out. With it, such a tool is adapted, the predicate the validator returns enforces the pattern on the tool's arguments, and the wire receives the server's source — or, where the target wire does not document `pattern`, a description stating it (see `schemaKeywords`). A validator `Failure` skips the tool, with the reason. Supply a validator built on an engine that is safe on hostile input — RE2, say. A plain `new RegExp(source)` defeats the point of the option. |
| <a id="property-schemakeywords"></a> `schemaKeywords?` | `readonly` | [`SchemaKeywordCapabilities`](https://github.com/ErikFortune/fgv/tree/main/libraries/ts-json-base/docs) | The keyword-capability table of the wire the adapted tools will be sent on, used to admit only tools that wire can carry. **Remarks** A tool whose schema that table refuses — today, one with a schema that states no `type` (pydantic `Any`, `{}`) on a wire that requires one or does not document it — is skipped like any other unadaptable tool, so one such tool cannot fail every request it would ride on. Get the table for a provider with `AiAssist.clientToolSchemaKeywords(descriptor, { model, endpoint, verifiedEndpoint })` from `@fgv/ts-extras`, passing exactly what the turn will be sent with. Defaults to `JsonSchema.unverifiedWireSchemaKeywords`, the conservative table, which refuses an untyped schema — so without this option such a tool is skipped. Pass the Anthropic-tools table (or any that passes untyped nodes) to have it adapted. Admission only: the adapted tool keeps the schema as `fromJson` parsed it, and the request path adapts it for the wire exactly once, when it is sent. The table must therefore be the one for the wire the tools are actually sent on: a tool admitted under a more permissive table than the request's wire makes `AiAssist.executeClientToolTurn` return a `Failure` naming the tool, the path and the wire, before anything is sent. |
