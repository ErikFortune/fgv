# Interface: IMcpHttpTransportParams

Parameters for [createHttpTransport](../functions/createHttpTransport.md). The transport connects to a Streamable-HTTP MCP
endpoint.

## Properties

| Property | Modifier | Type | Description |
| ------ | ------ | ------ | ------ |
| <a id="property-authprovider"></a> `authProvider?` | `readonly` | `OAuthClientProvider` | An OAuth 2.1 client provider, for servers that require the MCP authorization flow. The SDK attaches its access token to every request, refreshes it on a 401, and runs discovery and client registration as needed. **Remarks** **Interactive authorization runs only inside [connectMcpSession](../functions/connectMcpSession.md).** The provider's `state`, `saveCodeVerifier` and `redirectToAuthorization` are forwarded while the consumer's connect is in progress, and refused at any other time — on a later call, on the SDK's own reconnect of the standalone event stream, and on close. A refused step fails the operation with the `'unauthorized'` [McpFailureReason](../type-aliases/McpFailureReason.md); reconnect to authorize. For a flow that starts outside the window the refusal comes before any of the three has run. A flow that starts inside a connect which then times out or is aborted can already have passed `state` and `saveCodeVerifier` — and persisted what your provider persists there — and be refused only at `redirectToAuthorization`. `redirectToAuthorization` is also refused for a URL that is neither `https:` nor `http:` on a loopback host: the authorization endpoint comes from server-supplied metadata, so treat the URL as untrusted. **Non-interactive steps run wherever the SDK needs them**, including on its background reconnect of the event stream: discovery and `saveDiscoveryState`, client registration and `saveClientInformation`, a token refresh and `saveTokens`, and `invalidateCredentials` when the authorization server answers `invalid_grant` or `invalid_client`. After `redirectToAuthorization`, the connect fails `'unauthorized'`. Exchange the authorization code with the SDK's `auth()` (which saves the tokens through this provider) — **pass your guarded fetch as its `fetchFn`, or the token request bypasses the guard** — then connect again with a new transport. Static `headers` are never applied to a request for the authorization server: the package applies them only to requests whose URL is on the MCP endpoint's origin (for redirects, see [IMcpHttpTransportParams.headers](#property-headers)). The SDK is given a wrapper, not this object: a forwarding facade that gates the interactive steps. It is a different object from your provider, so an identity comparison against it fails. |
| <a id="property-fetch"></a> `fetch?` | `readonly` | [`McpFetch`](../type-aliases/McpFetch.md) | The `fetch` every HTTP request of the session goes through: each `POST`, the standalone `GET` event stream, and the `DELETE` that [closeMcpSession](../functions/closeMcpSession.md) sends. **Remarks** **Use `SaferFetch.createGuardedFetch` with `SaferFetch.blockPrivateNetworks()`** (both from `@fgv/ts-extras`). That gives MCP egress the same SSRF protection as every other safer-fetch call — the address guard on every hop, redirects rejected by default — without buffering the long-lived event streams. A refusal fails the operation with the `'egress-blocked'` [McpFailureReason](../type-aliases/McpFailureReason.md). Every refusal is also logged at `detail` to the session's logger, by its kind only — including one no operation waits on, such as the standalone event stream or the OAuth discovery the SDK runs after a 401 on its background reconnect. **Size `headersTimeoutMs` to your longest MCP request timeout.** The guarded fetch's headers deadline (default 10 s) runs from each request until its response headers arrive. A server that answers with JSON rather than an SSE stream holds a `tools/call`'s headers until the tool finishes, so a 15 s tool fails at 10 s — as `'timeout'` — whatever `timeoutMs` the call was given. Set `headersTimeoutMs` on `createGuardedFetch` to at least your longest `timeoutMs`. The package cannot see the guarded fetch's deadline, so it does not warn. Refusals are recognized by class, so the guarded fetch must come from the same `@fgv/ts-extras` this package resolves (it is a peer dependency): one from a second installed copy classifies as `'transport'`. **Any other `fetch` gets no protection from this package.** When omitted, the platform's `globalThis.fetch` is used, which connects to any address — including a private one — and the same is true of any function supplied here that does not guard. A custom `fetch` is still the right seam for a metered or pinned egress path. Redirects are then bounded only by the SDK's own default `redirectPolicy: 'same-origin'`: it calls the fetch with `redirect: 'manual'` and, for a fetch that honours that, follows a redirect that keeps the method and the origin (or goes from http to https on the same host) and fails the request on any other. If the guarded fetch allows redirects, list the static credential headers above and `mcp-session-id` in its `sensitiveHeaders`: `fetch` strips only `authorization` on a cross-origin redirect. With an [IMcpHttpTransportParams.authProvider](#property-authprovider), OAuth discovery, client registration and token requests go through this `fetch` too — so the guard also covers the authorization server the MCP server names. |
| <a id="property-headers"></a> `headers?` | `readonly` | `Record`\<`string`, `string`\> | Optional static headers (e.g. an `Authorization` bearer token or an `x-api-key`). Each name may appear once: header names are case-insensitive, so `X-Api-Key` and `x-api-key` together are refused rather than sent as one combined value. The headers are **copied** when [createHttpTransport](../functions/createHttpTransport.md) is called: changing or adding to this record afterwards has no effect on any request. Create a new transport to change them. They are applied by the package, **only to requests whose URL is on the MCP endpoint's origin** — never to the authorization server or any other origin. There a static header replaces one of the same name (a static `Authorization` overrides the OAuth provider's bearer token, as the SDK's own merge did). **Redirects.** The package sees only a request's first URL, so what happens on a redirect is the `fetch`'s. Without a consumer `fetch` (`globalThis.fetch`), a request carrying static headers refuses redirects (`redirect: 'error'`), because the platform would carry them to any origin. With a guarded fetch, its default `redirectPolicy: 'reject'` holds; under `'validate-each-hop'` a static header crosses a redirect to another origin unless it is listed in `sensitiveHeaders`. A consumer `fetch` of any other kind is called by the SDK with `redirect: 'manual'`. If it honours that, the SDK follows only a method-preserving redirect within the origin; if it ignores it, the fetch's own redirect handling applies. |
| <a id="property-url"></a> `url` | `readonly` | `string` | Absolute `http`/`https` URL of the MCP server endpoint. |
