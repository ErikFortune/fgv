| [`file-tree`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-json-base/src/packlets/file-tree) | `FileTree`, `FsTree`, in-memory tree — abstract directory/file traversal that works across Node/browser/zip/in-memory backends. **Default to `FileTree` for any file/directory access — only fall back to raw `fs` if you have a concrete reason it cannot work.** Optional **binary (raw bytes) capability**: `IBinaryFileTreeAccessors`/`IMutableBinaryFileTreeAccessors` (accessors) and `IBinaryFileTreeFileItem`/`IMutableBinaryFileTreeFileItem` (file items) — narrow with `isBinaryAccessors`/`isMutableBinaryAccessors`/`isBinaryFileItem`/`isMutableBinaryFileItem`. Byte **reads** (`getFileBytes`/`getRawBytes`) ship on all six adapters (Node `fs`, in-memory, zip, browser FSA, `localStorage`, HTTP); byte **writes** (`saveFileBytes`/`setRawBytes`) ship only on Node `fs` — every other backend persists text, so a byte write could not round-trip. **The file-item guards narrow the type only; they are not a success guarantee** — `FileItem` implements both binary interfaces unconditionally and delegates to its accessors, reporting a non-capable store as a `Failure` rather than omitting the method. Use the **accessor**-level guards (`isBinaryAccessors`/`isMutableBinaryAccessors`) when the check itself must guarantee success. Optional **strict-text capability** — a UTF-8 decode that **fails loudly on malformed input** instead of substituting U+FFFD the way the lenient WHATWG default does: `IStrictTextFileTreeAccessors.getFileTextStrict` / `IStrictTextFileTreeFileItem.getTextStrict`, narrowed with `isStrictTextAccessors` / `isStrictTextFileItem` (same guard semantics as the binary pair — the **accessor** guard is the real capability check). **The capability is about custody of the bytes, not about the adapter.** A store can only answer *"was this valid UTF-8?"* if it still holds the original bytes, so it is decidable **per file**, not per store: Node `fs` and zip entries are byte-native and decode strictly, a byte-seeded in-memory file decodes strictly, and a `string`- or JSON-seeded file **fails** — the substitution (if any) happened upstream, and re-encoding the decoded string always yields well-formed UTF-8, so a success would be a green light from a check that cannot fail. That rule is what makes the string-backed browser stores correct for free: `HttpTreeAccessors` (whose REST `contents` field is a JSON string) and `LocalStorageTreeAccessors` implement the capability and refuse **every** file, structurally rather than by a per-adapter special case. **Don't hand-roll `new TextDecoder('utf-8', { fatal: true })` over `getFileBytes()`** — over HTTP those "bytes" are a re-encode of an already-decoded string, so that recipe succeeds with nothing left to check. Optional **byte-native child create**: `IMutableBinaryFileTreeDirectoryItem.createChildFileBytes(name, bytes)`, narrowed with `isMutableBinaryDirectoryItem` — it exists because `createChildFile` is string-only, so the alternative is create-a-placeholder-then-`setRawBytes`, which leaves an empty file behind when the byte write turns out to be unsupported. The item guard is (as ever) narrowing only, but here **the answer is reachable from the item**: `canCreateChildFileBytes()` reports what the backing store will actually do, in the same spirit as `getIsMutable()`. **Copying a tree: use `copyItemInto(source, destinationDir, options?)` / `copyContentsInto(sourceDir, destinationDir, options?)`** — see the copy decision shortcut. |
| [`json-schema-builder`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-json-base/src/packlets/json-schema-builder) (namespace `JsonSchema`) | Typed JSON Schema for the **LLM-tool subset** — author the schema once, derive everything else. Seven factories (`JsonSchema.string`/`number`/`integer`/`boolean`/`enumOf`/`array`/`object`) plus the `optional` modifier return **`ISchemaValidator<T>`** instances that extend `Validator<T>` — **the schema value IS the validator**, call `schema.validate(input)` directly. `JsonSchema.Static<typeof schema>` derives the TypeScript type automatically — no caller-supplied `T`, no assertion. `schema.toJson()` emits the draft-07 wire schema (suitable for an LLM provider's tool `parameters` — optionality becomes the parent's `required` array). `JsonSchema.isSchemaValidator(value)` narrows an unknown `Converter`/`Validator` to `ISchemaValidator<unknown>` — the guard that lets a callee *look* and do more with a schema than with a bare validator (emit `toJson()` onto a wire); it narrows to `unknown` deliberately, since `_type` is a node-kind discriminant carrying no evidence about `T`. `JsonSchema.fromJson(raw)` parses a raw `JsonObject` (e.g. an MCP-discovered schema) into an opaque `ISchemaValidator<JsonValue>` (runtime validation, no static `T`), failing with a JSON-pointer path on out-of-subset structural keywords (`$ref`, `oneOf`/`anyOf`/`allOf`, `not`, `if`/`then`/`else`, `pattern`, union `type` — **except** the nullable spelling `[<type>, 'null']`, which it parses back into a `nullable` node so an emitted schema survives `toJson()` → `fromJson()`; the proxy path reconstitutes forwarded schemas that way, so a parser that refused the emitter's own output would break every nullable schema over it). Numeric validation is strict by default (rejects `'42'`; opt out with `number({ strict: false })`); objects are strict by default (`additionalProperties` defaults `false`, opt in with `{ additionalProperties: true }`). **`nullable: true` on any factory** widens `Static<S>` to `T \| null`, accepts `null`, and emits the draft-07 union `type: ['string', 'null']` — the spelling OpenAI strict mode accepts for an absent-able field, where `optional(...)` is *unsendable* because every property must appear in `required`. A nullable `enumOf` carries `null` in **both** `type` and `enum`, so the two halves of the node cannot disagree. **The option's name is not the wire spelling**: it never emits the OpenAPI keyword `nullable: true`, which OpenAI ignores — the Gemini adapter in `@fgv/ts-extras` translates to that dialect at its own edge. `optional` and `nullable` compose (`optional(string({ nullable: true }))` is absent-or-null-or-string) and are different questions: absent vs. present-and-null. **Use this instead of authoring a JSON Schema and a separate Converter for the same shape — the validator is derived from the schema, so they cannot drift.** Subset only: no `$ref`, polymorphism, `pattern`, custom formats, or JSON Schema 2020-12 features. |

## Decision shortcuts

- **Reading files (Node, browser, or zip)?** → `FileTree` from `@fgv/ts-json-base/file-tree` (+ `ts-extras/zip-file-tree` or `ts-web-extras/file-tree` for the backend).
- **Need a file read that fails loudly on malformed UTF-8 instead of silently substituting U+FFFD?** → narrow with `FileTree.isStrictTextAccessors` and call `getFileTextStrict(path)` (or `isStrictTextFileItem` + `getTextStrict()`) from `@fgv/ts-json-base/file-tree`. **Don't hand-roll `new TextDecoder('utf-8', { fatal: true })` over `getFileBytes()`** — the capability is about custody of the bytes, and over HTTP or `localStorage` those "bytes" are a re-encode of an already-decoded string, so the hand-rolled recipe *succeeds with nothing left to check*. `FsTree` and zip entries decode strictly; an in-memory tree decides per file (byte-seeded yes, string/JSON-seeded refuses); `LocalStorageTreeAccessors` and `FileSystemAccessTreeAccessors` refuse everything; **`HttpTreeAccessors` refuses under its default and decides honestly when constructed with `contentEncoding: 'base64'`** (which makes the server send bytes instead of a lenient decode of them — see `@fgv/ts-http-storage`). A refusal means *"this store cannot tell you"* — distinct from a decode failure, which means *"these bytes are not valid UTF-8"*. Note the capability code has no HTTP special case: base64 simply gives that store custody, and the general per-file rule does the rest.
- **Copying a file or a whole directory tree between `FileTree`s?** → `FileTree.copyItemInto(source, destinationDir, options?)` (one item, by name) or `FileTree.copyContentsInto(sourceDir, destinationDir, options?)` (the directory's contents, not the directory) from `@fgv/ts-json-base/file-tree`. **Don't hand-roll `getRawContents()` → `createChildFile()`** — that is a text read feeding a text write, which is lossless right up until something that is not UTF-8 lands in the tree, and then it silently mangles it. The helpers carry bytes verbatim where the destination store is byte-native, and as text only after **verifying that the text re-encodes to exactly the source bytes** — which is not the same as a successful strict decode, because `TextDecoder` strips a leading BOM that `TextEncoder` does not put back. Anything that would arrive changed is a `Failure` naming the path; pass `{ onUnfaithfulFile: 'skip' }` to get an `ICopyReport.skipped` entry instead, and reach for it deliberately — a file that cannot be carried is often a file that should not have been in the set, and the failure is the diagnosis. The report splits `filesCopiedAsBytes` from `filesCopiedAsText` **by mechanism, not outcome** (both are byte-faithful) so an audit can tell which route a snapshot actually took. A copy is **not atomic**: every file is attempted, so a failure names every offending path and the destination keeps whatever succeeded.
- **Loading/saving JSON files?** → `JsonFsHelper` from `@fgv/ts-json-base/json-file`.
- **Parsing a JSON-shaped string (with optional inner validation)?** → `Converters.stringifiedJson(inner?)` from `@fgv/ts-json-base/converters`.
- **Need typed JSON Schema for LLM tool authoring (one declaration → derived type + validator + wire schema)?** → `JsonSchema` from `@fgv/ts-json-base`. Author with `JsonSchema.object({ ... })` (factories: `string`/`number`/`integer`/`boolean`/`enumOf`/`array`/`object` + the `optional` modifier); `JsonSchema.Static<typeof schema>` derives the static type with no assertion; **the schema IS a Validator** — call `schema.validate(input)` directly (no separate `toConverter` step); `schema.toJson()` gives the draft-07 wire schema for the provider's tool `parameters`; `JsonSchema.fromJson(raw)` parses an MCP-discovered `JsonObject` into an opaque `ISchemaValidator<JsonValue>` for runtime validation. **Don't author a schema and a separate Validator for the same shape — they are the same object and cannot drift.** Strict numeric + strict object are the defaults (LLM convention). LLM-tool subset only (no `$ref`/`oneOf`/`pattern`/custom formats).
- **Need an absent-able field in a schema you send to OpenAI?** → **`nullable: true`, not `optional(...)`**. OpenAI strict structured output requires *every* property to appear in `required`, so a schema carrying `JsonSchema.optional(...)` is refused up front by `hasOptionalProperties` and routed through `onUnsupported` (degrading to unconstrained by default). `JsonSchema.string({ nullable: true })` keeps the key required, widens `Static` to `string | null`, and emits `type: ['string', 'null']` — the spelling OpenAI documents and the one it actually honours (it **ignores** the OpenAPI keyword `nullable: true`). Gemini wants the opposite spelling and `toGeminiParameterSchema` translates, so the same authored schema is correct on all five capable providers. **Do not fake absence with a sentinel** — an empty string mapped back to absent by the converter is exactly the schema-and-check drift the one-object design exists to remove, reintroduced one layer down. Anthropic and Gemini have no all-required rule and accept either.
