[libraries/ts-agent-memory](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-agent-memory)

App-agnostic **storage + retrieval substrate** for agent memory and knowledge — a FileTree-backed markdown + YAML-frontmatter vault (git-trackable, cross-runtime via `@fgv/ts-json-base` `FileTree`). The consumer owns its curation / processing / composition; this package owns persistence, identity, typed bodies, attributed edges, dedup, write policy, retrieval, and the optional-layer seams. **Small invariant core + optional present-when-wired layers.**

**Core.** `IMemoryEnvelope` (branded `MemoryId` / `EntityId` / `Kind` / `Tag` / `LinkType` / `MemoryScopeKey`; store-owned transaction-time `created` / `updated` / `seq`; `contentHash`; structured extensible `IProvenance`; optional `temporal?` / `embeddingRef?`), `IEdge` (**attributed object edges** — `type` / `target` / `confidence?` / `provenance?` / `valid_at?` / `invalid_at?` — never bare strings), per-kind body via `IBodyConverterRegistry` (`register` / `registerSchema` / `has` / `getConverter` / `convert` — consumer registers each kind's typed body Converter or `JsonSchema`; **no `any`**). `IIdentityCodec` maps a consumer domain key ⇄ `{ scope, idStem }` (**no minted UUIDs — `entityId` IS the domain address**); ships `KnowledgeIdentityCodec` (`<docId>`), `LtmIdentityCodec` (`<conversationId>`), `MtmIdentityCodec` (`<conversationId>:<turnIndex>` → `conversations/<id>/turn-<n>`).

**Store.** `FileTreeMemoryStore.create({ root, registry, codecs?, defaultCodec?, writePolicies?, index?, embedKinds?, scopeEncoding?, observers?, logger?, clock? })` → `IMemoryStore` (`get(kind, entityId)` codec-routed, `getById(scope, id)`, `list(selection)` (**the selection is required and must narrow** — see the listing decision shortcut), `listEntries()` (envelopes, no file reads), **`coverage()`** (per-kind derived-state health for `rank` / record vectors / fragment vectors from an envelope-only walk plus one count per wired index — **cheap by contract**, so a future addition needing a record body does not belong on it; note the index counts *are* I/O on a durable backend and can fail, which is why it returns a `Result`), **`reconcile(kind, artifact)`** (targeted, non-destructive repair of one lane for one kind — **replaces `reconcileRank`**, which is gone with no alias), `put(record)`, `delete(kind, entityId)` — all `Promise<Result<…>>`). Per write: body-validate → `Crc32Normalizer` content hash over `{ kind, body, links }` → **per-kind dedup** (`dedupScope: 'content'` = cross-id collapse for knowledge; `'entity'` = same-id idempotent only, so distinct entities never collapse — declared by `MemoryCapCullPolicy` / `TemporalVersionedPolicy`, and the `DEFAULT_DEDUP_SCOPE` a policy that declares nothing falls back to; note a kind with **no registered policy** resolves through the store's default `KnowledgeLwwPolicy` and therefore gets `'content'`. Read the effective value via **`IMemoryStore.dedupScopeFor(kind)`** — the one owner, consulted by the store's write path and the ingest orchestrator alike) → `IWritePolicy` admission (`KnowledgeLwwPolicy` last-write-wins; `MemoryCapCullPolicy` cap-cull-oldest over the `(scope, kind)` cohort + RFC-7386 **JSON Merge Patch** over `mutableFields`, composing `@fgv/ts-json` `JsonEditor` with `{ nullAsDelete: true, arrayMergeBehavior: 'replace' }`) → store-stamped `seq` / `created` / `updated` inside a write-lock → persist-then-evict (durability-first) → derived-index patch. Single-writer per store; the markdown files are the source of truth, the in-memory index is rebuilt on `create()`. **`index?: IMemoryIndex`** is an additive injection point (omitting it is byte-identical to before — a fresh `MemoryIndex` as always); when supplied, the store uses it for *every* index operation and holds no second index, including the write-path `entries()` reads (content-hash dedup, write-policy admission cohort, and the temporal versioned write/delete paths that derive an entity's version history from the index). A `null` index is treated as absent, same as every sibling optional param.

**Partial read: the index holds envelopes, not records.** Every `IMemoryIndex` read — `entries` / `byKind` / `byTag` / `byRecency` / `byRank`, plus the new O(1) keyed **`get(target)`** — returns **`IIndexedMemoryEntry`** (`scope` + `envelope`, **no body**). Selection has never needed a body: every filter the store and the retrievers apply reads envelope fields. Returning whole records made *every conforming index* hold *every body* by construction, which was the store's resident-memory ceiling; it is now removed from the contract rather than from one implementation. (This supersedes the previous note that an injected index was an instrumentation seam and not a memory fix — that was true of the old read surface and is why this redesign happened.) A caller that needs a body materializes it explicitly, through `getById` or an **`IMemoryRecordResolver`**; a lazy `body` getter was rejected because it would have kept every call site compiling while turning a memory read into a file read behind an unchanged type.

**`patch` writes, `rebuild` reads.** `patch` still takes a whole record (its caller is mid-write and holds one; it is also the one point a body-derived index could observe content without a re-read), but **`rebuild` takes projected entries** — a rebuild is a whole-vault *read* that happens to terminate in the index, and requiring records there would force every caller, the store's own open path included, to materialize N bodies to feed a structure that projects the envelope back out. That is what drops the open path's **peak body residency from N records to one**: the walk still parses and fully validates each body (which is what gives `onRecordError` its meaning) and then discards it.

**The conformance rule, replacing "only a faithful delegating decorator is safe":** an index is a derived, **complete, faithful** projection — an implementation may change *where* entries are stored and *how* they are looked up, never *which* entries exist or *what any envelope says*. The store's write path derives dedup matches, admission cohorts and version histories from these reads, so an index that hides an entry does not merely hide it from queries, it changes what the next write does. **Ordering is not part of the contract** and that is a *behavioural* break the compiler cannot find: the bundled `MemoryIndex` returns `Map` insertion order, which is stable and observable, so code that came to rely on it keeps compiling and changes results — use the ordered accessors.

**`IVectorIndex` carries backfill, coverage and membership.** The seam is `add` / `remove` / `query` **plus `size`** (the number of vectors held), **`rebuild`** (re-embed everything from an `IMemoryRecordSource`) **and `has(target)`** (does the index hold a vector for this record). All three are required, and the first two exist because their absence had a name: without `rebuild` on the contract a **persisted** index could not be backfilled at all — records written while it was unwired, a re-embed after a dimension change, and reconciliation after a swallowed embed-on-write failure were unreachable, and the store's own docstring promised a reconciliation the contract could not deliver for any index but the bundled one. Without `size`, a caller cannot distinguish *"the index is empty"* from *"nothing matched"*, since `query` answers an empty index with `succeed([])` and an "is semantic search wired?" check stays true while it holds nothing. `SqliteVecVectorIndex` implements all three, so the swap from the bundled index to the persistent one now type-checks **including** the place that backfills.

**`has` is what makes a repair targeted rather than a rebuild**, and it is the only way to see the record-lane inconsistency that runs the *other* direction: the index holds the vector but the envelope lost its `embeddingRef` (a failure swallowed after the vector was committed). From the envelope that record is indistinguishable from a never-embedded one, and it needs a restamp and no embedder call at all — so an `embeddingRef`-only repair cannot even detect it, let alone avoid paying for it. **Don't hand-roll a coverage walk over `embeddingRef`** for the same reason.

**`IFragmentVectorIndex` now carries the same three, adjusted for its one-to-many keying**: `has(target)`, **`recordCount`** and **`fragmentCount`** (deliberately *not* `size` — on a 1:N index `size` is two-ways readable, and a reader arriving from `IVectorIndex.size`, which counts vectors, takes the wrong one silently), and a `rebuild` returning **`IFragmentVectorRebuildReport`** — the record report's per-kind rule applied verbatim, plus a `fragments` map for the fan-out. `SqliteVecFragmentIndex` implements all of them, closing **E4 on the fragment lane**: before this a persistent fragment index could not be backfilled at all, and the store's own reconciliation promise was undeliverable for it.

**Partial-tolerant rebuild, resolved by kind.** `InMemoryCosineIndex.rebuild(source, embed, options?)` returns an **`IVectorRebuildReport`** on a `DetailedResult` (see the failure-carries-it note below) rather than a bare count — because a count cannot distinguish the ways a record can be absent from an index, and **`declined` was intentional, `excluded` was never offered, `skipped` was a fault**. **Every count in the report is `ReadonlyMap<Kind, number>`** (`indexed` / `declined` / optional `excluded`; `skipped: ISkippedVectorRecord[]` stays per-record, which already implies per-kind and carries the error besides). The rule, and it is on the type's docstring so the next field does not re-open it: *a coverage report exists to answer "is my coverage what I intended?", and no bare total can — `indexed: 500` reads identically whether the right kinds were indexed or a policy drift silently redirected coverage. Totals are derivable by summing; the breakdown is derivable from nothing else, since `IVectorQueryHit` carries no `kind`, `query` answers "what is near this", and `size` is a scalar. **A new count added to this report is resolved by kind unless there is a stated reason it cannot be.*** `indexed` is the count most tempting to leave bare and the most dangerous to, being the one a coverage surface renders. **`excluded` is the one optional count, and the optionality is semantic**: it is the only number the rebuild cannot know for itself (the `embedKinds` filter is applied upstream in `IMemoryRecordSource.list()`, which now returns an **`IMemoryRecordListing`** — `records` plus the `excluded` tally), so `undefined` means *this source does not report exclusions* and an empty map means *it does and excluded nothing*. A store-backed source always reports. `options.onRecordError` mirrors the store's open-time mode and **defaults to `'fail'`, preserving the historical all-or-nothing-to-empty contract exactly**; `'skip'` opts into the lenient shape, keeping the healthy records and returning every casualty structurally (target + error) so a caller can name and re-drive the loss. **It reports more, never less** — the point is to stop one bad record emptying an entire index, not to make failures quieter. A **list** failure stays fatal under both modes: an unreadable source says nothing about which records exist, so there is no honest partial to report. **A failure carries the report too**: `rebuild` returns `DetailedResult<IVectorRebuildReport, IVectorRebuildReport>`, and a `'fail'`-mode abort hands back what the attempt had established on the `detail` — coverage is most wanted exactly when a rebuild did not finish. The `'fail'` contract is otherwise **unchanged** (still resets, still aborts, still fails), so that report describes *the attempt*, not the surviving index, which is empty; only a success report describes what the index holds. A failure carries no detail only when nothing was attempted: always the `list` failure, and additionally whatever pre-loop step an implementation needs before it can start — `SqliteVecVectorIndex` must clear its table, and a failure to do so is such a case. Those disturb nothing and so have nothing honest to describe.

**Per-kind index participation.** Additive **`embedKinds?: ReadonlySet<Kind>`** on the store's create params declares which kinds take part in the **record-granular** vector index; **absent means every kind does**, so omitting it is byte-identical to before. Read it back through **`IMemoryStore.embedsKind(kind)`** — a total, synchronous, non-`Result` accessor in the same spirit as `dedupScopeFor`, so the store's write path and any caller reasoning about coverage cannot disagree. **This is not the same thing as a `MemoryEmbedder` decline, and the difference is cost**: a decline has already been *called* (the round trip is paid, and on a locally-hosted model that round trip IS the expense), whereas an excluded kind is never handed to the embedder at all — the decline makes the intent expressible, this makes it free. The exclusion also applies to **`asRecordSource()`**, which exists to drive `IVectorIndex` rebuilds, so a reopen does not re-embed kinds the index will never return; `listScoped()` is unfiltered and still returns everything — and, since the index was projected to envelopes, it **reads a file per record and can fail** where it previously read nothing and could not. It is complete or failed, never quietly short: a dropped record would land in none of `records` / `excluded` / `indexed` / `declined` / `skipped`, which is the same undercount this tally exists to prevent. A concurrent cap-cull eviction mid-walk therefore fails the call — see `docs/FUTURE.md`. `asRecordSource()` also **counts what it filters**, onto the listing's `excluded` map — it is the layer where the decision is made and therefore the only one that can, and without it those records land in none of `indexed` / `declined` / `skipped` so a caller computing coverage undercounts *in the direction of looking healthier*. Two costs motivate it: embedder work on the **critical path** for bookkeeping rows no query returns, and — the easier one to miss — **un-queried kinds crowding the `topK` window**, since `IVectorIndex.query` applies `topK` *before* any kind filter the retriever adds, so over-fetching to compensate silently loses recall exactly when the un-queried kinds score well. Record-granular only; the fragment path is independent, and a kind may legitimately be fragment-embedded but not record-embedded. An exclusion reaches the same conclusion as a decline — this record is intentionally not embedded — so it takes the same path on write: an inherited `embeddingRef` is dropped and the vector it named is pruned after the commit. That is what makes **narrowing `embedKinds` on an existing vault** safe rather than a silent inconsistency, since otherwise every previously-embedded record of a now-excluded kind would keep claiming an embedding the store will never refresh while its vector kept answering queries.

**Retrieval.** `IMemoryRetriever` + `IMemoryQuery` carrying `semantic?` / `asOf?` present-but-optional plus capability flags — **stable against a future semantic / temporal backend with no resignature**. Ships `RecencyRetriever` / `TagRetriever` / `StructuredFilterRetriever` / `LinkTraversalRetriever` (bounded, cycle-safe BFS over the derived backlink index) + `HybridRetriever` (capability-union, injectable `IMergeStrategy`); `SemanticRetriever` **degrades loudly** (`Result.fail`) until an `IVectorIndex` is wired. **`IMemoryQuery.provenanceSource`** is the attribution axis — **exact match on `envelope.provenance.source`**, the "show me everything this source produced" query for review, attribution, and retraction after a bad ingest. Deliberately *not* a subset match over the whole `IProvenance` block, a presence check, or a match on `by` / `model` / the consumer-owned extension keys: `source` is the only field of that block the library assigns meaning to, and `provenance` is **required** on every envelope, so the axis partitions the vault rather than silently dropping records that omit a field. It is applied by the shared pre-filter (`indexedRecordMatchesQuery`), so **every** retriever narrows by it and it composes as AND with `scope` / `kind` / `tag`; `StructuredFilterRetriever` additionally treats it as a **dispatch** axis, so a query whose *only* axis is `provenanceSource` is answerable there rather than falling through its `filter`-absent guard to an empty success. Not exposed on the L2 `memory_search` tool schema — attribution and retraction are operator concerns, not model-facing turn concerns. **Fragment-granular (sub-document) retrieval** ships alongside the record-granular path (N-Ask5): the **`IFragmentVectorIndex`** seam is a *sibling* of `IVectorIndex` (NOT a subtype — an index keyed by `(target, locator)` has no well-defined single-vector `add`) exposing `addFragments` (whole-record-replace) / `remove` / `query(vector, topK, options?)` where **`IFragmentQueryOptions`** is `{ maxPerRecord?, scope?, id? }` — the `scope` / `id` pair is the record narrowing, applied **during selection, before the `topK` cut**, and `scope` alone (no `id`) is the versioned-kind case, covering every version of an entity; **`IVectorQueryHit`** carries two additive optional identity fields, **`locator?`** (an *advisory* `[start, end)` span — the region of the body a fragment was derived from, **NOT** a slice guaranteed to reproduce its text, since a rewriting segmenter may not leave the fragment as a substring at all) and **`fragmentId?`** (an opaque consumer-minted bytestring, stored and returned verbatim, never parsed, never in the query path). The same pair is optional on **`IEmbeddedFragment`**, where **at least one of the two is required** — enforced by **`embeddedFragmentConverter`** (and re-checked by both index impls), deliberately *not* by a conditional-required union. **No single field discriminates a fragment hit from a record hit, and the disjunction is not offered as a discriminator either** — fragment-ness is determined by *which index produced the hit* (`IFragmentVectorIndex.query` vs `IVectorIndex.query`); note `locator` absence now means either "record-granular hit" or "fragment with no honest span". Fragment-id stability across re-embeds is the **consumer's** responsibility (whole-record-replace re-emits the whole set); the library's guarantee is only "we never parse it". **`MemoryEmbedder`** resolves to `Float32Array | undefined`, where **`undefined` means *intentionally not embedded*** — a deliberate decline, distinct from a `Failure` (which means the embedder tried and could not). A declined record is stored with no `embeddingRef`, no failure, and **nothing logged**; on the rebuild path it is counted on `IVectorRebuildReport.declined` (per kind) and deliberately kept OUT of `skipped` (which now formally means *a fault*), and on the ingest path it resolves `'new'` rather than erroring, so declining a kind never makes that kind un-ingestable. A decline on a record that **was** embedded (a re-put after the embedder's policy narrowed) drops the inherited `embeddingRef` *and* removes the stale vector — clearing the reference alone would be worse than doing nothing, since the index entry would survive and keep answering queries on the record's **superseded** content while the record itself claimed not to be indexed. The `remove` runs only when a reference was actually inherited, so the ordinary decline (a record never embedded) still costs no index round trip; a failed `remove` is logged and the reference is dropped regardless, best-effort like the rest of the vector path. Reach for it when a kind is a control or bookkeeping row no query should return — before this existed the only way to say "not this one" was `fail`, which is indistinguishable from an embedder outage in the logs. **`FragmentEmbedder`** is the chunk-and-embed sibling of `MemoryEmbedder`; it expresses a decline as an empty fragment array, which is **not** the same mechanism — an empty array still calls `addFragments(target, [])` (a real whole-record-replace, which is what clears any stale fragments), whereas a `MemoryEmbedder` decline skips the index entirely; **`InMemoryFragmentCosineIndex`** is the brute-force in-package impl; and **`FragmentSemanticRetriever`** is the discovery-half retriever that returns per-fragment `IVectorQueryHit`s (`{ target, locator, score }`) rather than records — so it is deliberately **NOT** an `IMemoryRetriever` (memory recall stays record-granular; sub-document knowledge uses the distinct fragment index) and degrades loudly when unwired. The store's additive **`fragmentIndex?` / `fragmentEmbedder?`** create params wire best-effort fragment-embed-on-write + removal on delete/eviction, independent of (and composable with) the record-vector `vectorIndex` / `embed` pair. `maxPerRecord` is applied during selection, before the topK cut. **`IMemoryQuery.filter` is applied by every retriever**, and the paging rule is part of the contract rather than an implementation detail: with no filter, ordering and paging run over envelopes and **only the page is materialized**, so `limit` bounds the *read*; with a filter (a predicate over the whole record) every envelope-survivor must be read, filtered, and *then* paged. Retrievers route through the shared `materializePage` rather than open-coding it — five of them silently stopped applying `filter` when the predicate moved out of the envelope pre-filter, at 100% coverage and with every test passing. **Observe.** `MemoryObservationStore` (ring-backed via `RetainingRingBuffer`; schema-aware `query`; the store fires `read` / `write` / `delete` observations when `observers` are wired, zero overhead otherwise). A `'write'` observation carries **`embed?: MemoryEmbedOutcome`** (`'embedded'` | `'declined'` | `'excluded'` | `'failed'`), with a matching **`embed` query axis**. This is the per-record answer to *"is this record in the index, and if not, why?"* — a question `embeddingRef` alone cannot answer, because its absence is **three-ways ambiguous** (declined / excluded / failed) and the put's own `outcome` is `'success'` in all three, embed-on-write being best-effort by design. `'failed'` covers both an embedder failure and an index `add` failure (the diagnostic logger names which; the coverage answer — *needs a re-embed* — is the same). **Absent means no outcome is being reported** — nothing wired, a dedup no-op that attempted nothing, or a **failed** write (an embed step may have run first, and can even leave an orphan vector a later `rebuild` reconciles; the field answers *"is this **stored** record in the index?"*, and a failed write produced no stored record). So `embed` is a property of successful writes. An `embed` criterion never matches a record carrying no outcome, so an unwired deployment does not read as a vault full of gaps. Record-granular only; the fragment path reports nothing here. **Don't derive index coverage from `embeddingRef` absence** — query the observations for the per-record *why*, and `IMemoryStore.coverage()` for the aggregate. **And never test `embeddingRef` for presence by hand: call `embeddingRefOf(envelope)`**, which returns the reference or `undefined` and is the one place `null`-vs-absent is collapsed. The field is `string | null | undefined` where `null` is the documented "not embedded" sentinel, so *both* obvious checks are wrong — `!== undefined` counts an embedding that is not there, `=== undefined` misses one that is missing — and neither mistake is a type error or visible to a coverage gate, because the sentinel is a **value** rather than a branch. All three in-repo call sites had one of the two bugs before this accessor existed.

**Ingest (L3).** `MemoryIngestOrchestrator.create({ store, registry, codecs?, classifier, extractor, relationExtractor, entityResolver?, vectorIndex?, embed?, similarityThreshold?, similarityTopK?, cycleGuard?, logger? })` → `IMemoryIngestOrchestrator` (`ingestItem` / `ingestBatch`). Six stages, host callbacks at classify / extract / resolve / relate and fgv-owned everything else: a typed body-validation boundary (no unchecked host body reaches the store), two-layer stage-4 dedup, stage-5 edge validation + a global-acyclicity cycle guard, provenance stamping, and the contradicts→temporal interlock. Every host callback is wrapped so a throw or rejection becomes a `Result.fail`. **Stage-4 layer 1** is fgv's deterministic exact `{ kind, body }` match and **honors the kind's `dedupScope`** — `'content'` matches scope-wide cross-id, `'entity'` matches only at the candidate's own entity address — read through `IMemoryStore.dedupScopeFor(kind)` so the ingest path and the store's own write path can never disagree. **Stage-4 layer 2** (only when `entityResolver` + `vectorIndex` + `embed` are all wired) embeds the candidate, surfaces over-threshold neighbors, and dispatches to the host `IEntityResolver`. A **`duplicate-of` verdict redirects sibling edges** built against the collapsed candidate onto the record it collapsed into, rather than orphaning them into a whole-item ingest failure. See `.claude/project/agent-memory-ingest-design.md` for the stage pipeline, both dedup layers, the verdict → write mapping, and the cycle guard.

**Agent tools (L2).** `createMemoryTools({ store, retriever, registry, codecs, tools?, ... })` → `ReadonlyArray<AiAssist.IAiClientTool>` — the `memory_write` / `memory_read` / `memory_search` / `memory_context` / `memory_delete` suite over a wired store + retriever, ready to hand to an LLM tool loop (`DEFAULT_MEMORY_TOOLS` is search + context).

**Shipped (v1):** the full substrate above (knowledge + experience kind families) **plus operational semantic recall** — `InMemoryCosineIndex` (brute-force in-package cosine `IVectorIndex`) + embed-on-write (consumer-injected embedder; the core stays embedder-agnostic — no `ai-assist` import) **plus fragment-granular (sub-document) retrieval** — `IFragmentVectorIndex` + `InMemoryFragmentCosineIndex` + `FragmentSemanticRetriever` + fragment-embed-on-write (N-Ask5; the durable backend `SqliteVecFragmentIndex` ships in `@fgv/ts-agent-memory-sqlite-vec`) **plus the temporal versioned write path + temporal retrievers** (`TemporalVersionedPolicy` invalidate-don't-delete, `TemporalIdentityCodec`, `CurrentValidRetriever` / `AsOfRetriever` / `HistoryRetriever`), **the L2 agent-tool surface**, and **the L3 ingest orchestrator** — the last three previously listed here as pending fast-follows, corrected 2026-08 after verifying against source. **There are no outstanding fast-follows.** **Use this for any agent memory / knowledge vault — do not hand-roll a record store, content-hash dedup, or backlink index.** First consumer: PersonAIlity (knowledge-first, behind its `IKnowledgeSearchProvider`).

## Decision shortcuts

- **Storing agent memory / a knowledge vault (records, dedup, attributed edges, backlink index)?** → `FileTreeMemoryStore` from `@fgv/ts-agent-memory`. Don't hand-roll a record store, content-hash dedup, or backlink index.
- **Semantic recall over that vault — record-granular vs sub-document?** → **Record-granular** (one vector per record; "which record matches"): wire the store's `vectorIndex` + `embed` and query via `SemanticRetriever`; the index is `InMemoryCosineIndex` (ephemeral) or `SqliteVecVectorIndex` (persistent). **Sub-document / fragment-granular** (many spans per record; "which record AND which `[start,end)` span matches" — the discovery half of search-then-read): wire the store's `fragmentIndex` + `fragmentEmbedder` and query via `FragmentSemanticRetriever` (returns per-fragment `{ target, score, locator?, fragmentId? }` hits, NOT records; supports a `maxPerRecord` cap). **To narrow the search to one record — or, for a versioned kind, to one entity across every one of its versions — pass `entityId` + `kind` on the `IFragmentQuery`** — they travel together because `kind` selects the identity codec, and the codec computes the storage address, so the resolution is a function and a colliding `entityId` across kinds is a non-issue rather than an ambiguity. **The narrowing is applied during selection, before the `topK` cut**, so the `topK` you ask for is the `topK` you get; filtering a global result afterwards is NOT equivalent, because it truncates across every record first and comes back short whenever other records outscore the target's fragments. For a **versioned** kind the narrowing covers *every version of the entity* — `TemporalIdentityCodec` files versions in their own per-entity subtree, so that subtree is the narrowing. **That is literal: superseded versions are invalidated but never pruned from the fragment index, so a scope narrowing returns current and historical fragments alike and nothing on a hit distinguishes them.** Same behaviour as the record-granular vector lane; it is not currency filtering, and there is no `asOf` axis on fragment search. Wire it as `FragmentSemanticRetriever.create({ backend, identityResolver: store })`; a narrowing with no resolver wired **fails loudly** rather than quietly searching everything; the index is `InMemoryFragmentCosineIndex` (ephemeral) or `SqliteVecFragmentIndex` (persistent). A fragment carries at least one of `locator` (advisory span — not a reproduction guarantee) / `fragmentId` (opaque, never parsed); **do not branch on which one is present to decide what kind of hit you have — you know that from the index you queried.** The two paths are independent — wire either, both, or neither. **Don't hand-roll a cosine index, a fragment locator scheme, or a re-embed-on-open loop.**
- **Need to know whether a store's derived state (rank / record vectors / fragment vectors) is consistent with its records — or to repair it if not?** → **`IMemoryStore.coverage()`** to measure and **`IMemoryStore.reconcile(kind, artifact)`** to repair, both from `@fgv/ts-agent-memory`. Coverage is cheap enough to call on a health endpoint (an envelope walk plus one count per wired index — bounded I/O on a durable backend, hence the `Result`) and reports **`covered`** — what the store *believes*, from `embeddingRef` — separately from **`indexSize`** — what the index *holds*. Their disagreement is the free signal that a vault was reopened against a fresh in-memory index, where `embeddingRef` lies in the confident direction; **do not collapse them into a percentage**. `reconcile` is **targeted and non-destructive** — it asks `has(target)` per record and skips what is already held — and is the opposite of `IVectorIndex.rebuild`, which resets the index and re-embeds the whole vault. It names both its kind and its artifact because the lanes are independently wirable and their units are incommensurable (one vector per record vs. N). **Absent is never zero**: an `undefined` artifact member means *not derived here at all*; a wired-but-empty lane usually means something is wrong. **Don't hand-roll a coverage walk over `embeddingRef`** — it cannot see the index-holds-it-but-the-envelope-lost-it case, which is repairable with no embedder call. Note `coverage()` reports a lane whose *index* is wired, while `reconcile` requires index **and** embedder, so a half-wired store can legitimately report a gap it refuses to close.
- **Need to measure a `FileTreeMemoryStore`'s resident-memory / open-cost behavior?** → wrap the shipped `MemoryIndex` in a counting/timing delegating decorator and pass it as `FileTreeMemoryStore.create({ ..., index })`. The decorator must be **faithful**: an index may change where entries live and how they are found, never which entries exist or what an envelope says, because the store's write path reads it too.
- **Reading an envelope's embedding reference, or checking whether it has one?** → **`embeddingRefOf(envelope)`** from `@fgv/ts-agent-memory` — returns the reference or `undefined`, collapsing the `null` sentinel. **Do not compare `envelope.embeddingRef` to `undefined` yourself**: the field is `string | null | undefined` with `null` meaning *not embedded*, so `!== undefined` over-counts and `=== undefined` under-detects, and the compiler flags neither. Returning the value rather than a boolean is deliberate — a caller who needs the string gets the check for free, so there is no second, weaker way to ask.
- **Listing records from a store?** → `IMemoryStore.list(selection)` **requires a selection that narrows** by `scope` / `kind` / `tag`, and rejects one that does not — `asOf` is a temporal *projection*, not a narrowing, so it does not satisfy the requirement on its own. To read the whole vault deliberately, pass **`scanEveryRecord()`** (optionally `scanEveryRecord({ asOf })`). The two are **mutually exclusive at the type level** — `{ scanEveryRecord: true, kind }` is a compile error rather than a scan that silently drops the `kind`. This is `safer-fetch`'s `addressGuard` / `allowAnyAddress()` idiom on a second surface: it cannot be omitted, and `grep -rn scanEveryRecord` enumerates every whole-vault read in a codebase. It buys **explicitness, not a cost bound** — `{ kind }` on a vault dominated by that kind still materializes most of it. **If you only need to select, use `listEntries()`** — every entry's scope and envelope, no selection required and no files read. The L2 `memory_search` tool enforces the same shape at the model boundary: at least one of `kind` / `tag` / `semantic` / `limit`.
- **Building a retriever directly?** → they take `{ index, resolver }` (`IRetrieverCreateParams`); **`IMemoryStore` extends `IMemoryRecordResolver`**, so the wiring is `{ index, resolver: store }` for the interface handle, not only for a concrete `FileTreeMemoryStore` — which also means any `IMemoryStore` implementation or test double must supply `resolveRecord` (and `listEntries`). With **no `query.filter`**, ordering and paging run over envelopes and only the page is materialized — so `limit` bounds the **read**, not just the result. That holds because both shipped comparators order on envelope fields; an ordering keyed on a body field would have to sort after materialization. **With a `filter`** (a predicate over the whole record) every envelope-survivor must be read first, so pair it with an envelope axis when the read cost matters.
