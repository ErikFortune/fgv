| [`crypto-utils`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-extras/src/packlets/crypto-utils) | Cross-runtime crypto surface. **`ICryptoProvider`** interface with operations: `encrypt`/`decrypt` (AES-256-GCM), `deriveKey` (PBKDF2), `sha256`, `generateRandomBytes`, `generateUuid`, `toBase64`/`fromBase64`, `generateKeyPair`/`exportPublicKeyJwk`/`importPublicKeyJwk` (asymmetric keypairs), `wrapBytes`/`unwrapBytes` (ECIES), `sign`/`verify` (digital signatures — algorithm inferred from key; supports Ed25519 and ECDSA-P256), `hmacSha256`/`verifyHmacSha256` (HMAC-SHA256 MAC computation and constant-time verification), `timingSafeEqual` (constant-time byte comparison — browser impl uses XOR-walk accumulator, Node impl delegates to `crypto.timingSafeEqual`); **`NodeCryptoProvider`** (Node implementation — pair with `BrowserCryptoProvider` from `ts-web-extras` on the browser side). **`KeyPairAlgorithm`** union: `'ecdsa-p256'`, `'rsa-oaep-2048'`, `'ecdh-p256'`, `'ed25519'`, `'x25519'` (X25519 Diffie-Hellman key agreement — use `deriveBits`/`deriveKey` to produce a shared secret). **`IArgon2idProvider`** / **`IArgon2idParams`** — interface for Argon2id key derivation; **`ARGON2ID_OWASP_MIN`** and **`ARGON2ID_PASSPHRASE`** — OWASP-recommended parameter presets. Obtain an implementation from `@fgv/ts-extras-argon2` (Node) or `@fgv/ts-web-extras-argon2` (browser/WASM). **`IKeyDerivationParams`** — discriminated union (`'pbkdf2'` | `'argon2id'`) for serializable key-derivation metadata. **`KeyStore`** — **the answer for password hashing and key storage**: password-protected vault for symmetric keys, API keys, and asymmetric keypairs; `addSecretFromPassword` derives + stores a key from a password via PBKDF2; `verifySecretFromPassword` does constant-time verification; `addSecretFromPasswordArgon2id` / `verifySecretFromPasswordArgon2id` — same workflow via Argon2id (pass an `IArgon2idProvider`). Also supports `addSecret`, `addKeyPair`, lock/unlock/save/changePassword, with optional `IPrivateKeyStorage` backend for private keys. Two concrete backends ship: **`EncryptedFilePrivateKeyStorage`** (here, Node — one AES-256-GCM-encrypted JWK file per key via FileTree I/O; consumer-supplied 32-byte encryption key; `supportsNonExtractable: false`) and **`IdbPrivateKeyStorage`** (`@fgv/ts-web-extras` — IndexedDB, stores `CryptoKey` objects directly; `supportsNonExtractable: true`). **Multibase/SPKI helpers** (new): `exportPublicKeyAsMultibaseSpki`/`importPublicKeyFromMultibaseSpki` — export/import any `ICryptoProvider` public key as a multibase base64url-encoded SPKI blob (algorithm-agnostic, suitable for storage/transport); `multibaseBase64UrlEncode`/`multibaseBase64UrlDecode` — pure base64url helpers with the `'m'` multibase prefix. **`toBase64`/`fromBase64`/`fromBase64Strict`** — standard-alphabet base64. **The two decoders differ in failure mode, and that is the point**: `fromBase64` is `Buffer`-first where a `Buffer` exists, and `Buffer.from(s, 'base64')` *silently discards* out-of-alphabet characters, so a corrupt payload decodes to plausible garbage; **`fromBase64Strict` returns `Result<Uint8Array>` and fails loudly** (`atob`-based; it does inherit the WHATWG forgiving-base64 leniency toward embedded ASCII whitespace, which is deliberate — line-wrapped base64 is benign). Reach for the strict one whenever the base64 came from somewhere you don't control (a wire response, a file, user input) and malformed means *something is wrong* rather than *do your best*. `DirectEncryptionProvider`, `createEncryptedFile`/`decryptFile`/`tryDecryptFile` for one-off encrypted JSON artifacts. **`HpkeProvider`** — HPKE base mode (RFC 9180): `DHKEM(X25519, HKDF-SHA256) + HKDF-SHA256 + AES-256-GCM`; `create(subtle)` factory; `sealBase(recipientPublicKey, info, aad, plaintext)` / `openBase(recipientPrivateKey, info, aad, enc, ciphertext)`; `HpkeProvider.encodeEnvelope` / `decodeEnvelope` for wire transport; `hkdf(secret, salt, info, length)` for standalone HKDF-SHA256. Works identically on Node.js 20+ and modern browsers via `SubtleCrypto` injection; re-exported from `@fgv/ts-web-extras` for browser callers. **Runtime requirements**: Node 20+; Chrome 113+, Safari 16.4+, Firefox 118+ (X25519 in Web Crypto). **Use this for any hybrid public-key encryption; do not roll your own KEM or HKDF.** **Use this for any password hashing, password-derived key, encrypted-at-rest artifact, named-key lookup, public-key export, digital signing/verification, or constant-time byte comparison; do not roll your own PBKDF2 / timing-safe compare / base64url.** |
| [`safer-fetch`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-extras/src/packlets/safer-fetch) | **An HTTP fetch primitive with an explicit threat model.** Not a Result-integration boundary and deliberately not thin — `fetch` is a platform global, there is no upstream to wrap, and the opinion *is* the deliverable. Three entry points — **`saferFetchBytes` / `saferFetchText` / `saferFetchJson`** (the JSON one takes an optional `converter`, so `T` is runtime-evidenced and never caller-asserted) — each returning `DetailedResult<ISaferFetchResponse<T>, FetchFailureReason>`. **`addressGuard` is required and has no default**, so omitting it is a *compile* error: the one mechanism that reliably prevents a guarantee being implied but not delivered, and it makes every call site's posture greppable in one search. **`blockPrivateNetworks(options?)`** is the recommended Node guard — resolves each hop's host through `node:dns` `lookup` and requires **every** resolved address to be globally routable public unicast (reject-if-any), with `allowLoopback` / `allowHosts` / `allowPorts` / `allowInsecureHttp` relaxations that each name themselves in the guard's own name so a `'blocked-by-guard'` failure says which posture was in force; `https:` is required unless `allowInsecureHttp` is set. **`allowAnyAddress()`** is the named, deliberately uncomfortable opt-out (and the only honest choice in a browser). Four guard **seams**, not one: address (the SSRF boundary), request, response-headers (**`allowContentTypes([...])`** gates on `Content-Type` *before* the body is read), and response-body. `redirectPolicy` defaults to `'reject'`; **`'validate-each-hop'`** follows redirects with `redirect: 'manual'` and runs the full address guard on **every** hop before any connection — redirect following and the SSRF guard are one mechanism, since a guard that validated only the caller's URL is defeated by a single `302` to `http://169.254.169.254/`. Credential stripping on a cross-origin hop is **monotonic** (`A`→`B`→`A` never hands the token back), loop detection compares **guard-cleared** URLs on both sides, and the hop cap defaults to 5. Two deadlines, one budget: `timeoutMs` (overall, 30 s) and `headersTimeoutMs` (per attempt, 10 s). `maxResponseBytes` (5 MiB) is counted during the read over **decoded** bytes, so a lying `Content-Length` and a gzip bomb both trip it. **`retry`** is opt-in (`IRetryPolicy`): retryable set + never-retryable set, `GET`/`HEAD` only unless `retryNonIdempotent`, `Retry-After` honored on 429/503 **clamped to `maxDelayMs`** (it is attacker-controlled), exponential backoff with full jitter, retries consume the overall deadline rather than resetting it, and **every attempt re-runs the guard from hop 0 — a full re-walk, never a resume and never a cached verdict**, because a cached verdict would make retry its own DNS-rebinding amplifier. **Stated limits (read them):** DNS rebinding is open — the guard validates a resolved address and the transport re-resolves; the pinning seam (`IGuardVerdict.pinnedAddress` + `IFetchTransport`) exists and `platformFetchTransport` **fails** rather than ignoring a pin it cannot honor. `FetchFailureReason` is an internal-network scanning oracle — log it, never echo it. No egress accounting, no cookie jar/cache/conditional requests. **Use this for any server-side fetch of a URL you do not fully control; do not hand-roll a timeout + size cap + redirect loop.** Browser callers use `@fgv/ts-web-extras`'s `SaferFetch` — see the guarantee table in both READMEs for what the browser cannot offer. |

| [`ai-assist`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-extras/src/packlets/ai-assist) | LLM provider client + JSON-tolerant response handling. `callProviderCompletion`/`callProviderCompletionStream` (OpenAI, xAI, Anthropic, Gemini), provider/model registry, `AiPrompt`. **Model aliases (`@<provider>:<role>`).** A model string that begins with the `@` sigil (`MODEL_ALIAS_SIGIL`) is an fgv-owned alias resolved through the owning descriptor's `aliases` map (`IModelAliasMap`) to the current concrete provider id; **any string without a leading `@` is a raw provider id and passes through verbatim** (back-compat is structural — Ollama `model:tag` ids, dated snapshots, and every existing `modelOverride` are unaffected). Resolution is `Result`-returning and registry-gated: an unregistered `@alias` fails loudly (typo/unknown) rather than hitting the wire. `resolveModelAlias(descriptor, model)` resolves one string (following one `@fgv-alias → provider-native-alias` hop, cycle-guarded); `resolveProviderModel(descriptor, modelOverride, context?)` is the call-time chokepoint (ModelSpecKey walk THEN alias resolution) used by completion / streaming / image / embedding / client-tool paths. `resolveImageCapability`/`resolveEmbeddingCapability` (look up a model's `IAiImageModelCapability`/`IAiEmbeddingModelCapability` by id) also resolve the alias first — pass either an `@alias` or a concrete provider id and both prefix-match against the correct capability entry; before this, an unresolved alias silently fell through to the provider's catch-all `modelPrefix: ''` rule and returned a confidently wrong capability rather than failing or returning `undefined`. **Quality-tier axis (`base`/`advanced`/`frontier`).** On top of the alias layer, one cross-provider quality axis selects the *completion* model: `ModelSpecKey = 'base' \| 'advanced' \| 'frontier' \| 'image' \| 'embedding'`, and a completion/streaming call takes an optional `tier?: 'advanced' \| 'frontier'` request param (omit → `base`). The three tier keys are the **only** completion-model selectors; `image`/`embedding` select the non-completion modalities. **Cascade:** a tier request walks an ordered fallback list and takes the first key present — `frontier → advanced → base`, `advanced → base`, `base` — so a provider only declares the tiers it differentiates (OpenAI wires all three — `frontier` → `gpt-5.6-sol`, which works on Chat Completions; Anthropic, Gemini, and xAI omit `frontier` and cascade to their `advanced` model; the previous frontier target `gpt-5.5-pro` is Responses-API-only and stays `modelOverride`-only). `base` is the required floor and universal fallback; `image`/`embedding` keep flat `modality → base` behavior. **Composition, not competition:** thinking (reasoning effort) and tools (server-side tools) are orthogonal request/capability params — they ride on top of whatever model the tier picked and **never select a model** (`ModelSpecKey` carries no `thinking`/`tools` keys — they were removed when the tier axis landed). `tier: 'base'` + a thinking config resolves the cheap base model and sends the thinking param to it; every base model is thinking-capable, so thinking composes with any tier with zero capability checks. A `frontier + thinking` request is just a frontier-tier completion with the thinking param set. **Per-provider tier maps:** OpenAI `base @openai:mini → gpt-5.6-luna`, `advanced @openai:flagship → gpt-5.6-terra`, `frontier @openai:pro → gpt-5.6-sol` (the 5.6 family works on chat completions; the previous frontier target `gpt-5.5-pro` remains Responses-API-only and `modelOverride`-only, routed via `responsesOnlyModelPrefixes`); Anthropic `base @anthropic:sonnet → claude-sonnet-5`, `advanced @anthropic:opus → claude-opus-5` (frontier unset → cascades to opus); Gemini `base @google-gemini:flash → gemini-3.5-flash`, `advanced @google-gemini:pro → gemini-3.1-pro-preview` (frontier unset → cascades to pro), `image @google-gemini:flash-image → gemini-3.1-flash-image`, `embedding @google-gemini:embedding → gemini-embedding-001`; xAI `base @xai-grok:standard → grok-4.3`, `advanced @xai-grok:flagship → grok-4.5` (frontier unset → cascades to flagship), `image @xai-grok:imagine → grok-imagine-image-quality` (the cheaper `@google-gemini:flash-lite → gemini-3.1-flash-lite` and the non-tier `@openai:nano`/`@anthropic:haiku`/`@anthropic:fable` aliases are `modelOverride`-only). **Maintenance loop = one edit + a testbed run:** on a provider line rotation edit the single alias value in that descriptor's `aliases` map (a tier re-slot edits the one `defaultModel` slot → alias mapping, no alias rename so no `modelOverride` ripple), then run the per-provider testbed scenario against the live API to confirm the new id answers — consumers and `defaultModel` reference the stable alias/tier slot and never change. The alias layer covers **selection/default churn only** — capability-detection `idPattern` rules and the typed `*ModelNames` unions remain manual axes (see TECH_DEBT). **Every turn entry point takes the unified `{ system?, messages: IChatMessage[] }` request shape (`IChatRequest`)** — `messages` is the ordered conversation, the last entry is the current user turn and the preceding entries are history; history is always linearized before the current turn (no head/tail asymmetry). `AiPrompt.toRequest()` lowers a system+user prompt to this shape. The proxy wire body serializes `{ system?, messages }`. **For JSON-shaped completions use `generateJsonCompletion<T>({ converter, ... })`** — it appends a smart "raw JSON only" prompt hint and runs the response through `fencedStringifiedJson`, which strips Markdown fences, leading preamble, and trailing prose before validating with the caller's `Converter<T>` or `Validator<T>`. The bare `extractJsonText` helper is exported for callers that just need wrapper-stripping; `fencedStringifiedJson({ extractor, inner })` is the extension point for custom extractors. **Don't reimplement fence-stripping in consumers.** **Native structured output (`structuredOutput` on every **non-streaming** completion request; the streaming paths deliberately do not support it).** Rather than only *asking* for JSON in the prompt, a caller can **tell the provider** — `structuredOutput: { mode: 'schema', schema }` (a `JsonSchema.ISchemaValidator`, **the same object you validate the reply with**, so the wire schema and the check cannot drift — the cloud sibling of `@fgv/ts-extras-ollama`'s `chatStructured`) or `{ mode: 'json-object' }` (syntactic validity only, arbitrary shape). Four wire formats behind it, declared per model family on `IAiProviderDescriptor.structuredOutput: IAiStructuredOutputCapability[]` and longest-prefix matched **after** alias resolution (`resolveStructuredOutputCapability`): `openai-json-schema` (`response_format`), `openai-responses-format` (`text.format`), `gemini-response-schema` (`generationConfig.responseMimeType` + `responseSchema`, run through the same draft-07 sanitizer the Gemini tool path uses), and `anthropic-tool-forced` — Anthropic has **no** response-format field, so its mechanism is a forced synthetic tool, which is why `'tool-forced'` is a distinct enforcement value and not a spelling of `'schema'`. **`IAiCompletionResponse.structuredOutput: StructuredOutputEnforcement` is REQUIRED, not optional** (`'none'` | `'json-mode'` | `'schema'` | `'tool-forced'`): an optional field would make absence three-ways ambiguous — no capability / not requested / a build predating the feature — and disambiguating exactly that is what it is for. It reports what was **sent**, never whether *this* response conforms; that is your converter's answer and re-deriving it here would be a second source of truth. **An optional property is unsendable to the OpenAI strict formats** (every property must be in `required`), and that is refused rather than silently repaired — *unless* the property's node **already admits `null`**, in which case **`adaptOptionalToNullable: true`** hoists it into `required` instead of refusing the schema. The opt-in is not the caller asserting its validator tolerates `null`; the condition is read off the schema, so it cannot be asserted falsely. `optional(string({ nullable: true }))` accepts absent-or-null-or-value, so listing the key in `required` only removes the model's option to omit it and every permitted reply still satisfies the supplied schema — whereas a plain `optional(string())` rejects `null`, is not hoisted, and still refuses. Verification is `hasOptionalProperties` re-run on the rewritten schema, so a partly-hoistable schema degrades **whole** rather than going out half-adapted; the hoist is also gated on the format, so it is inert on Gemini and Anthropic, which have no such rule. **Prefer `optional(x({ nullable: true })) + adaptOptionalToNullable` to authoring a bare `nullable`** when absence is genuinely meaningful to you: the schema then states what your validator does rather than what one provider demands, and the provider accommodation stays in `resolveStructuredOutput` where it can be kept correct as providers change. **`onUnsupported` defaults to `'degrade'`, and that is only safe because the report is required** — degrade-and-tell-me is safe, degrade-silently is the failure this exists to remove, so the two are one decision. Pass `'fail'` for output that is persisted or put on a wire, where an unconstrained generation that happens to parse is worse than an error; leave it at `'degrade'` on paths *designed* to degrade. Structured output **conflicts with server-side tools on Anthropic and Gemini, for different reasons** — Anthropic's mechanism *is* `tools` + `tool_choice` (a wire-level clash), Gemini's lives in `generationConfig` and the exclusion is API-enforced — and that conflict **fails rather than degrading** (`onUnsupported` speaks to capability, not to a caller asking for two incompatible things). Under `'tool-forced'` the reply arrives in a `tool_use` block and is **re-serialized** into `content`, so `content` stays a JSON string on every provider and a converter never branches on which enforcement it got. **`generateJsonCompletion` adopts this for free**: `ISchemaValidator<T> extends Validator<T>`, so if you already author `converter` as `JsonSchema.object({...})` the library now sends it — **no new parameter** (which would reintroduce the converter/schema drift `JsonSchema` exists to remove), and a plain `Converter` carries no schema so existing callers are byte-for-byte unchanged and report `'none'`. Self-hosted providers (`ollama`, `openai-compat`) and `groq` declare **no** capability on purpose — any model can sit behind them, and a wrong capability claim is worse than none; they report `'none'` and the report makes that visible. **To find out *why* a JSON-shaped response failed to parse** (not just that it did), use `classifyJsonParseFailure(text)` → `JsonParseFailureReason` — a structural classifier (walks the JSON grammar; never regex-matches the engine's `JSON.parse` error string, so verdicts don't drift across Node/V8 versions) that names four property-name-position faults with `token` + `offset` (0-based into the original `text`, not the extracted substring): `unquoted-property-name`, `single-quoted-property-name`, `unterminated-property-name`, `elided-member`; everything else — including truncation, missing colons, and bad number literals — falls to the conservative `'unknown'` rather than guessing. **Total**: non-string input returns `'unknown'` instead of throwing, matching `extractJsonText`'s guard. **For image generation use `callProviderImageGeneration`/`callProxiedImageGeneration`** — supports OpenAI DALL-E 3 / gpt-image-1 (`openai-images`), xAI grok-imagine generations (`xai-images`) and edits (`xai-images-edits`), and Gemini image-output via generateContent (`gemini-image-out`). The layered options system provides top-level keys (`size`, `quality`, `seed`, `count`) alongside per-provider `models` blocks for provider-specific params (e.g. `{ provider: 'openai', family: 'gpt-image', config: { outputFormat, background, moderation, outputCompression } }`). Provider capability is declared on `IAiProviderDescriptor.imageGeneration: IAiImageModelCapability[]`; `imageOptionsResolver` translates the layered options into a wire-ready `IResolvedImageOptions`. **For harness-side client tools (tools the caller implements, not the provider) use `executeClientToolTurn`** — the single-turn helper for tool-use conversations. Supply `clientTools: IAiClientTool[]` alongside any `tools: IAiServerToolConfig[]`; the helper returns `{ events: AsyncIterable<IAiStreamEvent>, nextTurn: Promise<Result<IAiClientToolTurnResult>> }` where `events` streams intermediate tool events and `nextTurn` awaits the complete round-trip result (including `continuation.messages` — the provider-format wire messages to re-supply on the next turn). `IAiClientTool` carries `config: IAiClientToolConfig` (name, description, `parametersSchema: ISchemaValidator<TParams>` — use `JsonSchema.object(...)` from `@fgv/ts-json-base`) and `execute: (args: unknown) => Promise<Result<unknown>>`. Type the tool as `IAiClientTool` (unparameterized, default `unknown`) and validate args inside `execute` via `parametersSchema.validate(args)` — the `execute` callback is contravariant in `TParams` so a typed `IAiClientTool<{key:string}>` is not assignable to `IAiClientTool<unknown>`. For multi-turn conversations pass `continuationMessages: continuation.messages` (type `ReadonlyArray<JsonObject>`) — `continuation.messages` is **cumulative** (replace each round, do not manually concatenate; the library prepends the inbound tail automatically so the array always covers all rounds so far) — these are provider-format wire objects appended after the current user turn. The exact wire-shape handling is per-provider: **Anthropic** projects each entry to `{ role, content }` (extra fields dropped; invalid entries skipped); **Gemini** projects to `{ role, parts }` (same shape guard); **OpenAI Responses / xAI** pass entries through verbatim with a `JsonObject` guard (since OpenAI Responses items are a `type`-keyed discriminated union whose fields differ per item). Consumers should not assume arbitrary fields round-trip on every provider — the high-fidelity round-trip is on the OpenAI/xAI path; Anthropic and Gemini preserve only the projected fields. Cross-provider continuation works on **all four providers**. **Do not put continuation wire objects in `messages`** (the unified `IChatRequest` conversation turns) — `continuationMessages` is a distinct post-current-turn axis whose provider-native fields the normalized `messages` path would strip. `IResolvedThinkingConfig` is exported from the packlet for callers that pre-resolve thinking options (e.g. `{ anthropicEffort: 'low' }`) and pass them directly to `executeClientToolTurn`. **Tool parameters authored as `JsonSchema.object(...)` work transparently on Gemini** — the adapter sanitizes draft-07-only keywords (`additionalProperties`, `$schema`) recursively before submission, so strict-by-default schemas don't need consumer pre-processing. **Gemini API constraint:** Gemini's `generateContent` forbids combining built-in grounding (`web_search`) with function calling in the same request — pick one. The library **pre-empts this with a named `Result.fail` before any wire call**, so you get a legible refusal rather than the provider's `INVALID_ARGUMENT` HTTP 400. **Completion diagnostic:** `IAiStreamDone.incompleteReason?: string` (`@public`) carries the OpenAI/xAI Responses `incomplete_details.reason` (`'max_output_tokens'`, `'content_filter'`, …) when `truncated === true`; absent when the stream completed normally. **Provider-drift instrumentation:** Anthropic and OpenAI Responses adapters maintain a `RECOGNIZED_*_EVENTS` allowlist and log a one-time `logger.warn` per stream per unrecognized SSE event name. Warning starts with the stable `ai-assist:unrecognized-event` tag (filter on this prefix to alert on provider-API evolution); includes a **default-safe structural payload preview** (top-level JSON keys + length — never field values) for triage; names the allowlist constant so a developer can find the right list to update. Production deployments wire the `ILogger` via the streaming-call params (`IProviderCompletionStreamParams.logger` / `IExecuteClientToolTurnParams.logger` — NOT via the per-adapter `IStreamApiConfig`, which carries only `{ baseUrl, apiKey, model }`); deployments that don't (default `NoOpLogger`) get a silent no-op. Ops triaging an active drift signal can opt in to the **raw payload preview** by setting `AI_ASSIST_UNRECOGNIZED_EVENT_FULL_PAYLOAD=1` in the environment — keep this off in production by default since SSE payloads can carry tool args / user-conversation text / other sensitive content. Gemini-side drift instrumentation is queued (JSON-chunk wire shape doesn't fit the SSE-event-name allowlist concept). **For embeddings (`text → vector`) use `callProviderEmbedding`/`callProxiedEmbedding`** — the cross-provider embedding primitive (third modality alongside completion and image generation). Batch in (`input: string \\| string[]`), `number[][]` out, `Result`-wrapped. Two wire formats behind one dispatcher: `openai-embeddings` (`POST /embeddings`) serves **OpenAI** (`text-embedding-3-*`), **Ollama** (point `endpoint` at `http://localhost:11434/v1`), **openai-compat** self-hosted servers, and **Mistral** (`mistral-embed`); `gemini-embeddings` (`POST /models/{model}:batchEmbedContents`) serves **Google Gemini** (`gemini-embedding-001`) with its `taskType` retrieval-asymmetry knob. Capability is declared on `IAiProviderDescriptor.embedding: IAiEmbeddingModelCapability[]` (model-prefix matched, longest wins) and selects the model via the `embedding` `ModelSpecKey`. Knob handling (`dimensions`, `taskType`) is **no-op-where-unsupported, not a failure** — a caller passes `taskType: 'retrieval-query'` once and it maps to Gemini's wire `RETRIEVAL_QUERY` while being a logged no-op on the (symmetric) OpenAI-format providers, so the cross-provider call site never branches. Empty input short-circuits to an empty result with no wire call; a batch over the capability's `maxBatchSize` fails fast (no auto-chunking). xAI and Anthropic declare no embedding capability (no first-party endpoint) and reject up front. Vectors are `number[]` (not `Float32Array`) for JSON-wire fidelity — call `Float32Array.from(vector)` at the vector-store boundary; the library does not L2-normalize (Gemini MRL-truncated vectors may need it). |

## Decision shortcuts

- **Symmetric encryption / decryption (AES-GCM)?** → `DirectEncryptionProvider` or `KeyStore.encryptByName` from `@fgv/ts-extras/crypto-utils`, backed by `NodeCryptoProvider` (Node) or `BrowserCryptoProvider` (browser).
- **Need AES-256-GCM encrypt/decrypt with a key you already hold (PBKDF2/HKDF output, raw bytes)?** → `ICryptoProvider.encrypt(plaintext, key)` / `ICryptoProvider.decrypt(data, key, iv, authTag)` from `@fgv/ts-extras/crypto-utils`. The higher-level `DirectEncryptionProvider` and `KeyStore.encryptByName` paths wrap these for named-key lookup workflows.
- **Password-protected vault for keys / API keys / keypairs?** → `KeyStore` from `@fgv/ts-extras/crypto-utils`. Use `addSecretFromPassword` to derive + store, `verifySecretFromPassword` for constant-time password verification.
- **Need a private-key storage backend so `KeyStore.addKeyPair` works?** → **Node:** `CryptoUtils.KeyStore.EncryptedFilePrivateKeyStorage.create({ directory, encryptionKey, cryptoProvider })` — import `CryptoUtils` from `@fgv/ts-extras` (or the `@fgv/ts-extras/crypto` subpath); one AES-256-GCM-encrypted JWK file per key via FileTree; you supply the 32-byte `encryptionKey`; `supportsNonExtractable: false`. **Browser:** `CryptoUtils.IdbPrivateKeyStorage.create({ databaseName?, storeName? })` — import `CryptoUtils` from `@fgv/ts-web-extras` (IndexedDB; stores `CryptoKey` directly; `supportsNonExtractable: true`). Pass the instance as `KeyStore.create({ ..., privateKeyStorage })`. Don't roll your own `IPrivateKeyStorage`.
- **PBKDF2 key derivation, ECIES wrap/unwrap, asymmetric keypairs (Ed25519, ECDSA-P256, ECDH-P256, RSA-OAEP, X25519)?** → `ICryptoProvider` from `@fgv/ts-extras/crypto-utils`. Never call `node:crypto` or `crypto.subtle` directly.
- **Need to hash / verify a password (PBKDF2)?** → `KeyStore.addSecretFromPassword` / `verifySecretFromPassword` from `@fgv/ts-extras/crypto-utils`. Never roll PBKDF2 directly.
- **Need to hash / verify a password with Argon2id?** → `KeyStore.addSecretFromPasswordArgon2id` / `verifySecretFromPasswordArgon2id` from `@fgv/ts-extras/crypto-utils`, passing a `NodeArgon2Provider` (`@fgv/ts-extras-argon2`) or `BrowserArgon2Provider` (`@fgv/ts-web-extras-argon2`). Use `ARGON2ID_OWASP_MIN` or `ARGON2ID_PASSPHRASE` presets from `CryptoUtils` for OWASP-compliant parameters.
- **Decoding base64 that arrived from somewhere you don't control?** → `CryptoUtils.fromBase64Strict(s)` from `@fgv/ts-extras/crypto-utils` — `Result<Uint8Array>`, fails on malformed input. **Not `CryptoUtils.fromBase64`, and not `Buffer.from(s, 'base64')`**: both silently drop out-of-alphabet characters, so a corrupt payload decodes to plausible garbage and the corruption surfaces (if ever) far downstream. Use the lenient one only for base64 you produced yourself. **Don't hand-roll `atob` + a `charCodeAt` loop** — that recipe was independently reimplemented three times in this repo before being collapsed onto this primitive.
- **Need to encode/decode a public key as multibase SPKI?** → `exportPublicKeyAsMultibaseSpki(key, provider)` / `importPublicKeyFromMultibaseSpki(encoded, algorithm, provider)` from `@fgv/ts-extras/crypto-utils`. Pass the `ICryptoProvider` instance so the underlying SPKI export/import routes through the correct platform implementation.
- **Need hybrid public-key encryption (encrypt to a recipient's public key, one-shot)?** → `HpkeProvider` from `@fgv/ts-extras/crypto-utils` (Node) or `@fgv/ts-web-extras` (browser). `HpkeProvider.create(subtle).orThrow()` then `sealBase(recipientPub, info, aad, plaintext)` / `openBase(recipientPriv, info, aad, enc, ciphertext)`. Suite: DHKEM(X25519, HKDF-SHA256) + HKDF-SHA256 + AES-256-GCM (RFC 9180 base mode). `info` is mandatory and must be application-specific context bytes — empty `info` provides no context binding. Use `HpkeProvider.encodeEnvelope` / `decodeEnvelope` for wire transport. Never roll your own KEM.
- **Need standalone HKDF-SHA256 key derivation?** → `HpkeProvider.create(subtle).orThrow().hkdf(secret, salt, info, length)` from `@fgv/ts-extras/crypto-utils` (or `@fgv/ts-web-extras` for browser). Raw RFC 5869 HKDF — unlabeled, suitable for application-level key derivation.
- **Need X25519 key agreement?** → `generateKeyPair('x25519', ...)` from `ICryptoProvider` (`@fgv/ts-extras/crypto-utils`) to produce the keypair; use `ICryptoProvider.exportPublicKeySpki` / `importPublicKeySpki` to exchange public keys. Raw `deriveBits` for the shared secret is not yet wrapped by `ICryptoProvider` — do not call `crypto.subtle` directly.
- **Need to sign data or verify a signature (Ed25519, ECDSA-P256)?** → `ICryptoProvider.sign(privateKey, data)` / `ICryptoProvider.verify(publicKey, signature, data)` from `@fgv/ts-extras/crypto-utils`. Algorithm is inferred from the key's `algorithm` property — generate keys with `generateKeyPair('ed25519', ...)` or `generateKeyPair('ecdsa-p256', ...)`. Both return `Promise<Result<...>>`.
- **Need HMAC-SHA256 authentication / MAC verification?** → `ICryptoProvider.hmacSha256(key, data)` / `ICryptoProvider.verifyHmacSha256(key, signature, data)` from `@fgv/ts-extras/crypto-utils`. The verify variant uses `timingSafeEqual` internally for constant-time comparison. Both return `Promise<Result<...>>`.
- **Need constant-time byte comparison?** → `ICryptoProvider.timingSafeEqual(a, b)` from `@fgv/ts-extras/crypto-utils`. Returns `boolean` directly (not `Result`). Node impl delegates to `crypto.timingSafeEqual`; browser impl uses XOR-walk accumulator. Never use `===` or loop with early return for security-sensitive comparisons.
- **Asking an LLM for JSON and getting a validated `T`?** → `AiAssist.generateJsonCompletion<T>({ converter, ... })` from `@fgv/ts-extras/ai-assist`. Tolerates Markdown fences, preamble, and trailing prose by default. Don't reimplement fence-stripping in consumers. **Author `converter` as `JsonSchema.object({...})`** (from `@fgv/ts-json-base`) rather than `Converters.object({...})` and the library also *tells the provider* — one object is the wire schema and the reply validator, so they cannot drift, and there is no second parameter to keep in sync. A plain `Converter` still works and sends nothing.
- **Need the provider to constrain its output, not just be asked to?** → `structuredOutput` on any `callProviderCompletion` / `callProxiedCompletion` request: `{ mode: 'schema', schema }` for shape, `{ mode: 'json-object' }` for syntactic validity only. Read **`response.structuredOutput`** to learn what was actually enforced (`'none'` | `'json-mode'` | `'schema'` | `'tool-forced'`) — it is **required on every response**, because you cannot know up front which concrete model will serve you (a `tier` request cascades, aliases resolve at call time), so the report rides on the response rather than being a lookup you do yourself. It says what was **sent**, never whether *this* reply conforms — that is your converter's job and the library will not re-derive it. Unsupported combinations **degrade by default and say so**; pass `onUnsupported: 'fail'` when the output is persisted or put on a wire. **Don't hand-roll a `response_format` per provider** — the four wire shapes differ in more than field names, and Anthropic has none at all (it forces a tool, and the library re-serializes the tool input back into `content` so your converter does not branch).
- **Running a tool-use conversation with harness-side client tools?** → `AiAssist.executeClientToolTurn({ descriptor, apiKey, system?, messages, clientTools, tools?, model?, resolvedThinking? })` from `@fgv/ts-extras/ai-assist`. Like every turn entry point it takes the unified `{ system?, messages }` request shape (the last `messages` entry is the current user turn; preceding entries are history). Returns `{ events, nextTurn }` — consumer drives the outer multi-turn loop. Pass `continuationMessages: continuation.messages` on subsequent turns — `continuation.messages` is **cumulative** (replace each round, do not manually concatenate); do NOT put continuation wire objects in `messages` (they are a distinct post-current-turn axis). Works on **all four providers** (Anthropic, OpenAI Responses, Gemini, xAI via OpenAI). Type client tools as `IAiClientTool` (unparameterized) and validate args inside `execute` — the callback is contravariant in `TParams`. Author the `parametersSchema` with `JsonSchema.object(...)` from `@fgv/ts-json-base`; `schema.validate(args)` is the round-trip verify step. **Gemini-specific:** cannot combine `web_search` (built-in grounding) with client tools in the same request — Gemini's API HTTP-400s on that combination; pick one.
- **Diagnosing an OpenAI/xAI Responses stream that completes empty?** → Check `IAiStreamDone.incompleteReason?: string` on the `done` event. `'max_output_tokens'` → reasoning + tools consumed the output budget (raise the cap or shorten the prompt); `'content_filter'` → safety filter blocked the response. Absent → stream completed normally; if you still see no text, pass an `ILogger` to the streaming call (`callProviderCompletionStream({ ..., logger })` or `executeClientToolTurn({ ..., logger })`) and look for `ai-assist:unrecognized-event` warns — the streaming adapter probably saw an event family it doesn't handle yet (provider-API evolution).
- **Alerting on provider-API evolution affecting `@fgv/ts-extras/ai-assist`?** → Pass an `ILogger` via the higher-level streaming params (`IProviderCompletionStreamParams.logger`, `IExecuteClientToolTurnParams.logger`, etc.) and filter on the stable `ai-assist:unrecognized-event` warn prefix. The streaming helpers thread the logger down to the per-adapter unknown-event sites; the per-adapter `IStreamApiConfig` itself is just `{ baseUrl, apiKey, model }` and is not where consumers wire the logger. The Anthropic and OpenAI Responses adapters maintain per-stream-dedup'd allowlists of recognized SSE event names; an unrecognized event triggers one warn per stream per name including a length-capped structural payload preview (top-level JSON keys + length by default; raw payload via the `AI_ASSIST_UNRECOGNIZED_EVENT_FULL_PAYLOAD` env var). Use this in production to alert when a provider's wire shape changes (likely class of issue: adapter parse miss → silent feature degradation). Gemini's drift instrumentation is queued separately (different wire shape).
- **Stripping LLM Markdown fences from raw text?** → `AiAssist.extractJsonText` (default extractor) or `AiAssist.fencedStringifiedJson({ extractor, inner })` (extension point) from `@fgv/ts-extras/ai-assist`.
- **Diagnosing *why* an LLM's JSON response failed to parse (not just that it did)?** → `AiAssist.classifyJsonParseFailure(text)` from `@fgv/ts-extras/ai-assist` — returns a typed `JsonParseFailureReason` (four named property-name-position faults with `token`/`offset`, else `'unknown'`); structural, not regex-on-engine-message; total (non-string input → `'unknown'`, never throws). Branch on the reason to repair the cheap cases, re-prompt the expensive ones, or fail outright — don't regex-match `JSON.parse`'s message.
- **Generating images from an LLM provider?** → `AiAssist.callProviderImageGeneration({ descriptor, apiKey, params })` from `@fgv/ts-extras/ai-assist`. Use `callProxiedImageGeneration(proxyUrl, ...)` to route through a proxy when direct browser calls are CORS-restricted. Pass top-level options (`size`, `quality`, `seed`, `count`) and a `models` array for provider-specific config blocks.
- **Declaring image generation capability on a provider?** → Add `imageGeneration: IAiImageModelCapability[]` to `IAiProviderDescriptor`. Each capability entry carries `format` (`'openai-images' | 'xai-images' | 'xai-images-edits' | 'gemini-image-out'`), `modelPrefix`, and optional flags like `acceptsImageReferenceInput`, `defaultOutputMimeType`, `outputParamStyle`, `supportsQualityParam`, `maxCount`.
- **Looking up a model's image/embedding capability by id?** → `AiAssist.resolveImageCapability`/`resolveEmbeddingCapability` from `@fgv/ts-extras/ai-assist`. Both resolve an `@alias` before prefix-matching, so pass either an alias or a concrete provider id — both resolve to the correct capability entry rather than an alias silently matching the provider's catch-all rule.
- **Enabling extended thinking / reasoning on LLM completions?** → Pass `thinking: IThinkingConfig` to `callProviderCompletion` or `callProviderCompletionStream`. `IThinkingConfig` supports a cross-provider generic `effort?: 'low' | 'medium' | 'high'` shorthand and an optional `providers[]` array for per-provider config blocks. Provider-specific types: `IAnthropicThinkingConfig` (effort), `IOpenAiThinkingConfig` (effort, including `'none'` to re-enable temperature), `IGeminiThinkingConfig` (thinkingBudget integer), `IXAiThinkingConfig` (effort). Model-specific and `'other'` escape-hatch blocks let you override for individual models without affecting others. Merge precedence: generic effort → provider-generic blocks → model-specific/other blocks (later declaration wins within a tier). **Temperature + thinking conflicts**: Anthropic and OpenAI (non-`'none'` effort) and xAI return `Result.fail`; Gemini accepts both. Thinking content is discarded in this phase; caller-visible thinking-event surfacing is the scope of the followup stream `ai-assist-thinking-events`. Unknown/unsupported providers silently ignore the `thinking` field.
- **Embedding text via a cloud or self-hosted provider (OpenAI / Gemini / Ollama / openai-compat / Mistral)?** → `AiAssist.callProviderEmbedding({ descriptor, apiKey, params: { input, dimensions?, taskType? }, modelOverride?, endpoint? })` from `@fgv/ts-extras/ai-assist`; `callProxiedEmbedding(proxyUrl, ...)` to route through a backend proxy. `input` is `string | string[]`; the result's `vectors[i]` aligns to `input[i]`. Pass `dimensions` (honored by OpenAI `text-embedding-3-*` and Gemini) and/or `taskType` (Gemini retrieval asymmetry, e.g. `'retrieval-query'` vs `'retrieval-document'`) — both are a **logged no-op** on providers/models that don't support them, never a failure, so a cross-provider call site passes them once. Self-hosted (`'ollama'`/`'openai-compat'`) needs an explicit `modelOverride` (no default embedding model). xAI / Anthropic have no embeddings endpoint and reject up front. **Don't reach for `@fgv/ts-extras-transformers` for this** — that's the in-process path; this is the distant-HTTP path (see the three-way decision shortcut above).
- **Calling a self-hosted Ollama or OpenAI-compatible model?** → Use the `'ollama'` or `'openai-compat'` provider descriptor from `AiAssist.getProviderDescriptor`. Both are `needsSecret: false` — pass `apiKey: ''` and the library omits the `Authorization` header automatically. The `'ollama'` descriptor defaults to `http://localhost:11434/v1`; `'openai-compat'` has `baseUrl: ''` and requires an explicit `endpoint`. **`defaultModel` is `''` for both** — always supply `model` explicitly (e.g. `model: 'llama3.2'`). Pass `endpoint` to override `baseUrl` per call for `callProviderCompletion`, `callProviderCompletionStream`, and `callProviderListModels`. (`executeClientToolTurn` takes the same `endpoint` override, resolved through `resolveEffectiveBaseUrl`.) **Browser CORS:** Ollama only allows requests from `localhost` by default; set `OLLAMA_ORIGINS=*` (or a specific origin) in the Ollama server environment before starting it, otherwise browser calls will be blocked by the CORS preflight.
- **Fetching a URL you do not fully control (server-side)?** → `saferFetchJson` / `saferFetchText` / `saferFetchBytes` from **`@fgv/ts-extras/safer-fetch`**, with `addressGuard: blockPrivateNetworks()` (the option is **required** — omitting it is a compile error, which is the point). Add `responseHeadersGuard: allowContentTypes([...])` to reject on the header rather than after a body transfer, `redirectPolicy: 'validate-each-hop'` when ingesting real-world URLs (every hop is fully address-guarded before any connection, and credential stripping is monotonic), and `retry: { attempts: n }` when you want retry — it is off by default, consumes the overall deadline rather than resetting it, and re-runs the guard from hop 0 on every attempt. For a local sidecar, name every deviation: `blockPrivateNetworks({ allowLoopback: true, allowInsecureHttp: true, allowHosts: ['localhost'], allowPorts: [11434] })`. **Do not hand-roll a timeout + size cap + redirect loop, and do not echo `FetchFailureReason` to an untrusted caller — it is an internal-network scanning oracle.** DNS rebinding remains a documented open limit; a strict `allowHosts` list is the recommended mitigation.
- **Mustache rendering for LLM prompts (verbatim, no HTML escaping)?** → `MustacheTemplate.create(template, { escape: 'none' })` from `@fgv/ts-extras` (mustache packlet). The template string is the first argument; the options bag is second. Uses a per-instance `Mustache.Writer` — no mutation of the global `Mustache.escape`, so concurrent renderers with different escape strategies coexist. Default `'html'` preserves the existing back-compat behaviour; pass a `(value) => string` callback for a custom strategy. `@fgv/ts-prompt-assist` consumes the `'none'` strategy internally.
- **Knowing what a rendered template is *made of* — which part of the output came from which interpolation, and how big each part is?** → `MustacheTemplate.renderWithSegments(context)` from `@fgv/ts-extras` (mustache packlet). Returns `IRenderedTemplate` — the same `text` `render()` produces, plus `segments`: a document-ordered, contiguous, gapless attribution of every code unit to either literal template text or a named interpolation (`kind`, `name`, `start`, `length`, `escaped`). **Offsets are computed during the render, never recovered by searching the output** — searching is unsound for a value used twice, one that renders empty, one that is a substring of the surrounding literal text, and one that escaping alters, and it fails *silently* with plausible offsets. **Sections, inverted sections and partials are refused, not approximated** (they render non-linearly, so a map walked from the token order would mis-describe the result); comments and set-delimiter tags emit nothing and are skipped. Each interpolation is rendered from its already-parsed token via the same `Writer` primitives `render()` reaches through `renderTokens`, so value semantics — dotted paths, lambdas, `null` rendering empty, non-string coercion — are mustache.js's, and a mid-template delimiter change is invisible here rather than a hazard. The text is compared against `render()` before returning. Reach for `render()` when you only want the string.
- **CSV / record-jar?** → `@fgv/ts-extras` (`csv` / `record-jar`).
- **Numeric / date / orderable range?** → `RangeOf<T>` from `@fgv/ts-extras/experimental`.
