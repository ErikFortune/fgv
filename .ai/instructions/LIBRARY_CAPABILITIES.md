# FGV Library Capabilities Quick Reference

**Purpose:** Before writing new utility code, scan this guide. If a capability is listed here, use the existing library — do not reimplement it. Each entry links to the source on the `release` branch.

**Repository:** https://github.com/ErikFortune/fgv (release branch)

---

## How to use this guide

1. Find the capability area you need (parsing, validation, JSON, file trees, etc.).
2. Check the listed package/packlet for an existing implementation.
3. Follow the link to read the actual exports/API before coding.
4. Add the package via `rush add -p <name>` (see `MONOREPO_GUIDELINES.md`).

If you cannot find what you need here, ask before adding a new dependency or rolling your own.

## Foundational

### `@fgv/ts-utils` — core primitives
[libraries/ts-utils](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-utils)

| Packlet | Use for |
|---|---|
| [`base`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-utils/src/packlets/base) | `Result<T>` (`succeed`/`fail`/`captureResult`), `mapResults`/`mapDetailedResults`/`mapSuccess`/`mapFailures`/`allSucceed`/`firstSuccess`/`populateObject`, `MessageAggregator`, branded types (`Brand<T>`), normalization helpers, `generateUuid()` / `Uuid` / `isValidUuid` (cross-runtime UUIDv4 via `globalThis.crypto.randomUUID`). **Always use `Result<T>` for fallible ops.** **Async siblings of the whole family ship alongside them** — five **bounded-parallel collectors** (`mapResultsAsync` / `mapDetailedResultsAsync` / `mapSuccessAsync` / `mapFailuresAsync` / `allSucceedAsync`) over one scheduler, plus two **transitively-async, serial-by-contract** members (`populateObjectAsync`, `firstSuccessAsync`). Each async member mirrors its sync sibling's name, parameter order and fold. **They take *deferred* work (`AsyncDeferredResult<T> = () => Promise<Result<T>>`), never materialized `Promise<Result<T>>` — a promise that already exists has already started, so a collector handed one has nothing left to bound.** Two call forms per collector: the **thunk form** `f(work, options?)` (N *different* operations; makes the deferral visible) and the **`(items, fn)` form** `f(items, (item, index) => Promise<Result<T>>, options?)` (N applications of *one* operation; makes already-started work structurally inexpressible). Only the five collectors take `IAsyncResultOptions` (`concurrency?` defaulting to the exported finite `DEFAULT_RESULT_CONCURRENCY`, `aggregatedErrors?`); `populateObjectAsync` / `firstSuccessAsync` deliberately do **not**, because a `concurrency` field on a serial-by-definition operation would be a lie in the signature. **Results come back in input order regardless of completion order**; `map*` keeps scheduling after a failure and aggregates every error, and `allSucceedAsync` deliberately does *not* short-circuit (parity with `allSucceed` beats a faster failure path); a work function that throws synchronously or rejects becomes a `Failure`, never an escaped exception. Empty input matches the sync siblings exactly. No cancellation / `AbortSignal` (deferred; the retrofit is additive and verified non-breaking), and no retry / timeout / backoff — those belong to the caller's work function. |
| [`conversion`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-utils/src/packlets/conversion) | `Converters.{string,number,boolean,object,arrayOf,enumeratedValue,optionalField,...}` for transforming/parsing untyped input into typed values. **Use instead of manual `typeof` checks + casts.** |
| [`validation`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-utils/src/packlets/validation) | `Validators.{object,arrayOf,isA,oneOf,...}` for in-place validation of class instances or already-constructed objects. |
| [`collections`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-utils/src/packlets/collections) | `ResultMap`, `ValidatingResultMap`, `Collector`, `ConvertingCollector`, `ValidatingCollector`, `KeyValueConverters`. **Result-friendly:** operations return `Result<T>` so they drop directly into `.onSuccess` chains. Use instead of raw `Map`/`Record` when keys/values need validation. `RetainingRingBuffer<T extends { seq: number }>` — generic bounded most-recent-N ring with O(1) eviction, monotonic-`seq` cursor paging, and predicate filtering (`query({ sinceSeq?, limit?, filter? })`); `lastSeq` is stable across `clear()`. A **pure** storage substrate — the caller mints each record (assigning its own `seq`/`timestamp`); the buffer only retains/evicts/queries. Use it as the shared mechanism beneath any "retain the most recent N records, page by cursor, filter" surface (observation stores, structured-log rings) instead of hand-rolling a circular buffer. |
| [`hash`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-utils/src/packlets/hash) | `Crc32Normalizer`, `HashingNormalizer` — deterministic hashing/normalization of arbitrary objects. `Normalizer.canonicalize(value)` — RFC 8785 canonical JSON serialization: sorts object keys lexicographically (not numerically), emits directly to string (bypasses JS engine integer-key reordering). Available on `HashingNormalizer`, `Crc32Normalizer`, or any `Normalizer` subclass. Use for stable JSON fingerprinting, signing, or any protocol requiring byte-identical canonical form. |
| [`logging`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-utils/src/packlets/logging) | `Logger`, `LogReporter` — Result-friendly logger that can be inserted into a Result chain to log success/failure values without breaking the chain. `RetainingLogger` — bounded most-recent-N ring of structured `ILogRecord` (seq + timestamp + level + formatted message + raw `args`) with a `getRecords({ minLevel?, sinceSeq?, limit? })` query API (min-severity filter, since-cursor incremental paging, most-recent-N tail); seq is monotonic and stable across eviction. `MultiLogger` — fans every log call out to N child `ILogger`s, each applying its own threshold (e.g. feed a `ConsoleLogger` for stdout AND a `RetainingLogger` for an observability buffer from one pinned logger). Subclasses that need the structured form override the additive `LoggerBase._logStructured` hook (default no-op). |

### `@fgv/ts-utils-jest` — Result-aware Jest matchers
[libraries/ts-utils-jest](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-utils-jest)

`toSucceed`, `toFail`, `toSucceedWith`, `toFailWith`, `toSucceedAndSatisfy`, `toFailWithDetail`, `toSucceedAndMatchSnapshot`, plus `toFailTest*` for testing custom matchers. **Always use these in tests instead of `.orThrow()` + assertions.** Includes ANSI color stripping for stable cross-env snapshots.

## JSON

### `@fgv/ts-json-base` — types, validation, file I/O
[libraries/ts-json-base](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-json-base)

| Packlet | Use for |
|---|---|
| [`json`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-json-base/src/packlets/json) | `JsonValue`/`JsonObject`/`JsonArray`/`JsonPrimitive` type definitions. |
| [`json-compatible`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-json-base/src/packlets/json-compatible) | `JsonCompatibleType<T>` — compile-time check that a typed interface is JSON-serializable. |
| [`converters`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-json-base/src/packlets/converters), [`validators`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-json-base/src/packlets/validators) | JSON-shaped converters/validators (e.g. `Converters.jsonObject`, `Converters.jsonValue`, `Converters.stringifiedJson` — parses a JSON string then optionally validates with an inner `Converter<T>` or `Validator<T>`). |
| [`json-file`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-json-base/src/packlets/json-file) | `JsonFsHelper`, `JsonTreeHelper` — load/save JSON files, walk JSON trees. |
| [`file-tree`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-json-base/src/packlets/file-tree) | `FileTree`, `FsTree`, in-memory tree — abstract directory/file traversal that works across Node/browser/zip/in-memory backends. **Default to `FileTree` for any file/directory access — only fall back to raw `fs` if you have a concrete reason it cannot work.** Optional **binary (raw bytes) capability**: `IBinaryFileTreeAccessors`/`IMutableBinaryFileTreeAccessors` (accessors) and `IBinaryFileTreeFileItem`/`IMutableBinaryFileTreeFileItem` (file items) — narrow with `isBinaryAccessors`/`isMutableBinaryAccessors`/`isBinaryFileItem`/`isMutableBinaryFileItem`. Byte **reads** (`getFileBytes`/`getRawBytes`) ship on all six adapters (Node `fs`, in-memory, zip, browser FSA, `localStorage`, HTTP); byte **writes** (`saveFileBytes`/`setRawBytes`) ship only on Node `fs` — every other backend persists text, so a byte write could not round-trip. **The file-item guards narrow the type only; they are not a success guarantee** — `FileItem` implements both binary interfaces unconditionally and delegates to its accessors, reporting a non-capable store as a `Failure` rather than omitting the method. Use the **accessor**-level guards (`isBinaryAccessors`/`isMutableBinaryAccessors`) when the check itself must guarantee success. For a strict decode that fails loudly on malformed UTF-8 instead of the lenient WHATWG default: `new TextDecoder('utf-8', { fatal: true }).decode(bytes)`. |
| [`json-schema-builder`](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-json-base/src/packlets/json-schema-builder) (namespace `JsonSchema`) | Typed JSON Schema for the **LLM-tool subset** — author the schema once, derive everything else. Seven factories (`JsonSchema.string`/`number`/`integer`/`boolean`/`enumOf`/`array`/`object`) plus the `optional` modifier return **`ISchemaValidator<T>`** instances that extend `Validator<T>` — **the schema value IS the validator**, call `schema.validate(input)` directly. `JsonSchema.Static<typeof schema>` derives the TypeScript type automatically — no caller-supplied `T`, no assertion. `schema.toJson()` emits the draft-07 wire schema (suitable for an LLM provider's tool `parameters` — optionality becomes the parent's `required` array). `JsonSchema.fromJson(raw)` parses a raw `JsonObject` (e.g. an MCP-discovered schema) into an opaque `ISchemaValidator<JsonValue>` (runtime validation, no static `T`), failing with a JSON-pointer path on out-of-subset structural keywords (`$ref`, `oneOf`/`anyOf`/`allOf`, `not`, `if`/`then`/`else`, `pattern`, union `type`). Numeric validation is strict by default (rejects `'42'`; opt out with `number({ strict: false })`); objects are strict by default (`additionalProperties` defaults `false`, opt in with `{ additionalProperties: true }`). **Use this instead of authoring a JSON Schema and a separate Converter for the same shape — the validator is derived from the schema, so they cannot drift.** Subset only: no `$ref`, polymorphism, `pattern`, custom formats, or JSON Schema 2020-12 features. |

### `@fgv/ts-prompt-assist` — conditional prompt resolution
[libraries/ts-prompt-assist](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-prompt-assist)

ts-res-driven prompt authoring, organisation, and resolution for LLM workflows. Built on `@fgv/ts-res` (qualifier-conditional candidate selection), `@fgv/ts-extras` (`MustacheTemplate.create(template, { escape: 'none' })` for verbatim render; `AiAssist.fencedStringifiedJson` for fence-tolerant JSON output parsing; `Yaml.yamlConverter` for descriptor / bindings / qualifier-config loading), and `@fgv/ts-json-base` (`FileTree` for storage). **One YAML file per `(scope, prompt-id)`** holds the descriptor + all candidates; scope-level `_bindings.yaml` carries slot bindings; root-level `_qualifiers.yaml` carries ts-res `IQualifierDecl[]`. Key exports: **`PromptLibrary.create`** (factory; takes `store`, `qualifiers`, optional `registry` / `safetyPolicy` / `cacheListener` / `logger` / `observers`); **`PromptLibrary.resolve`** (chain-walks scopes, runs ts-res candidate selection on the supplied qualifier context, merges scope-level bindings cross-scope honouring `enforced` locks, recursively resolves resource bindings with RFC 8785 cycle-detection + depth cap, renders via Mustache with `escape: 'none'`, returns body + full `IPromptResolveTrace`); **`PromptLibrary.resolveJsonOutput<K>(req, rawOutput, expectedKind)`** (JSON pipeline strips fences → `JSON.parse` → typed Converter dispatched by `(id, kind)` → `outputValidations[]` chain narrowed by `value.kind`; runtime-verifies the descriptor's `output.kind === 'json'` AND that the descriptor's converter is registered to produce `expectedKind` before running the pipeline, so the return type `Extract<TResponse, { kind: K }>` is runtime-evidenced rather than caller-asserted); **`PromptLibrary.resolveFreeTextOutput(req, rawOutput)`** (runtime-verifies the descriptor's `output.kind === 'free-text'` and returns the raw output verbatim as `Result<string>` — no `TResponse` involvement); **`PromptLibrary.describe`** (descriptor lookup across scopes with cross-scope structural-equality check). Storage: **`FileTreePromptStore`** (read-only at v0.1; works against `FsTree` / in-memory / zip / browser FSA File Tree); **`PromptStoreFixture.build`** (seeds an in-memory FileTree from authored records — the canonical test/demo fixture; **no standalone `InMemoryPromptStore`**). Registry: **`PromptRegistry<TResponse>`** with three typed sub-registries (`converters` / `slotKinds` / `outputValidations`), parameterized by the consumer's response union (`TResponse extends { kind: string }`) so the JSON output pipeline flows the narrow Converter type end-to-end. Safety: **`IPromptSafetyPolicy`** carries `defaultMaxLength`, `screeners` (an ordered `IScreener[]` — pluggable, async, per-slot-value pre-render screening; each `screen(ctx)` returns `Promise<Result<ISafeguardFinding[]>>`), and `antiJailbreakPreface` (post-render seam — consumer supplies the framing). Screeners run sequentially in declaration order; a finding with `disposition: 'reject'` (or a screener returning `fail()`) fails the resolve and short-circuits the rest, while `'warn'` / `'info'` findings surface on `trace.safeguardFindings`. Findings carry open `kind`s (`SafeguardFindingKind = BuiltInFindingKind | (string & {})`), optional structured `metadata`, and `screener` attribution. **`createPatternScreener({ patterns, onMatch, screenedSources?, name? })`** is the built-in regex injection screener (reproduces the pre-pluggable semantics including `lastIndex` reset between values; `screenedSources` is the screener-owned source allowlist — omit it to screen every sourced slot). Custom screeners (ML classifiers, remote calls) implement `IScreener` directly. The descriptor-level `safeguards.skipInjectionScreening` still bypasses all screeners for a prompt; `defaultMaxLength` and `antiJailbreakPreface` stay policy-level primitives (not screeners). Observability: additive **`IPromptLibraryCreateParams.observers?: ReadonlyArray<IPromptObserver>`** — a fan-out fired once per public `resolve` / `resolveJsonOutput` / `resolveFreeTextOutput` call (never for nested resource-binding resolves; those roll up under the outer record's `trace.resourceBindingResolutions[].innerTrace`). Each **`IPromptObserver.observe(record): Promise<Result<unknown>>`** receives a `phase`-discriminated **`IPromptObservationRecord`** (`'resolve'` | `'json-output'` | `'free-text-output'`); output records cross-link to their resolve record via `linkedResolveSeq`; failure resolve records carry `error` only (no trace, v0.1). `seq`+`timestamp` are library-assigned (consistent across all observers); `contentHash` (CRC32 over canonical `{promptId,chain,qualifierContext,substitutions}`) is the dedupe key. **Observer errors never affect `resolve()`** — a failed `Result`, throw, or rejection is swallowed and logged to the injected `logger` at warn; set **`fireAndForget: true`** on a slow remote observer so it does not extend `resolve()` latency (awaited is the default). Default store **`PromptObservationStore.create({ maxRecords?, qualifierResolver? })`** implements `IPromptObserver`, retains records in a bounded `RetainingRingBuffer`, and answers schema-aware **`query(criteria)`** (by `promptId` / `scope` / `qualifiers` (delegated to the injected resolver) / `outputKind` / `outcome` / `phase` / safeguard disposition / `seq` + `timestamp` range). **Qualifier matching is delegated to an injectable `IQualifierResolver`** — the default `defaultStringEqualityQualifierResolver` does naive string equality on supplied (defined) axes, which is **deliberately narrower** than `PromptLibrary.resolve`'s ts-res-driven match (e.g. BCP47 `lang=fr-CA` records will NOT match a `lang=fr` query under the default). Deployments needing ts-res-equivalent semantics inject their own resolver; the swap is a pure implementation-of-interface change with no API surface churn on the store. **Most-permissive by design** — it stores `body` / `rawOutput` / `substitutions` verbatim; redaction + retention are deployment policy, not library policy: wrap the store with a redacting `IPromptObserver` or substitute it entirely. **Do not roll your own prompt-observation ring** — use `PromptObservationStore`, and for non-prompt retain-and-page surfaces use `RetainingRingBuffer` from `@fgv/ts-utils`. Branded ids: `PromptId` rejects `'::'`; `SlotName` matches the Mustache name production. **Use this for any LLM prompt that needs to vary on context (tenant, language, tone, region) or compose partial fragments over a shared base. Do not roll your own Mustache renderer for LLM prompts — the verbatim render + double-brace rejection are load-bearing.** v0.1 is **out of scope** for: write API (`put` / `putBindings` / `delete`), change notification (`watch`), LLM-call orchestration, editor UX, default anti-jailbreak content, free-text output validators. See the [README](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-prompt-assist#readme) for the quick-start.

### `@fgv/ts-agent-memory` — structured memory + knowledge substrate for agents
[libraries/ts-agent-memory](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-agent-memory)

App-agnostic **storage + retrieval substrate** for agent memory and knowledge — a FileTree-backed markdown + YAML-frontmatter vault (git-trackable, cross-runtime via `@fgv/ts-json-base` `FileTree`). The consumer owns its curation / processing / composition; this package owns persistence, identity, typed bodies, attributed edges, dedup, write policy, retrieval, and the optional-layer seams. **Small invariant core + optional present-when-wired layers.**

**Core.** `IMemoryEnvelope` (branded `MemoryId` / `EntityId` / `Kind` / `Tag` / `LinkType` / `MemoryScopeKey`; store-owned transaction-time `created` / `updated` / `seq`; `contentHash`; structured extensible `IProvenance`; optional `temporal?` / `embeddingRef?`), `IEdge` (**attributed object edges** — `type` / `target` / `confidence?` / `provenance?` / `valid_at?` / `invalid_at?` — never bare strings), per-kind body via `IBodyConverterRegistry` (`register` / `registerSchema` / `has` / `getConverter` / `convert` — consumer registers each kind's typed body Converter or `JsonSchema`; **no `any`**). `IIdentityCodec` maps a consumer domain key ⇄ `{ scope, idStem }` (**no minted UUIDs — `entityId` IS the domain address**); ships `KnowledgeIdentityCodec` (`<docId>`), `LtmIdentityCodec` (`<conversationId>`), `MtmIdentityCodec` (`<conversationId>:<turnIndex>` → `conversations/<id>/turn-<n>`).

**Store.** `FileTreeMemoryStore.create({ root, registry, codecs?, defaultCodec?, writePolicies?, index?, scopeEncoding?, observers?, logger?, clock? })` → `IMemoryStore` (`get(kind, entityId)` codec-routed, `getById(scope, id)`, `list(filter)`, `put(record)`, `delete(kind, entityId)` — all `Promise<Result<…>>`). Per write: body-validate → `Crc32Normalizer` content hash over `{ kind, body, links }` → **per-kind dedup** (`dedupScope: 'content'` = cross-id collapse for knowledge; `'entity'` = same-id idempotent only, so distinct entities never collapse — declared by `MemoryCapCullPolicy` / `TemporalVersionedPolicy`, and the `DEFAULT_DEDUP_SCOPE` a policy that declares nothing falls back to; note a kind with **no registered policy** resolves through the store's default `KnowledgeLwwPolicy` and therefore gets `'content'`. Read the effective value via **`IMemoryStore.dedupScopeFor(kind)`** — the one owner, consulted by the store's write path and the ingest orchestrator alike) → `IWritePolicy` admission (`KnowledgeLwwPolicy` last-write-wins; `MemoryCapCullPolicy` cap-cull-oldest over the `(scope, kind)` cohort + RFC-7386 **JSON Merge Patch** over `mutableFields`, composing `@fgv/ts-json` `JsonEditor` with `{ nullAsDelete: true, arrayMergeBehavior: 'replace' }`) → store-stamped `seq` / `created` / `updated` inside a write-lock → persist-then-evict (durability-first) → derived-index patch. Single-writer per store; the markdown files are the source of truth, the in-memory index is rebuilt on `create()`. **`index?: IMemoryIndex`** is an additive injection point (omitting it is byte-identical to before — a fresh `MemoryIndex` as always); when supplied, the store uses it for *every* index operation and holds no second index, including the write-path `entries()` reads (content-hash dedup, write-policy admission cohort, and the temporal versioned write/delete paths that derive an entity's version history from the index). **This is an instrumentation seam, not a resident-memory fix** — `IMemoryIndex`'s read surface returns whole records by construction, so any conforming index still materializes every body; an injected index changes WHERE records come from, not WHETHER bodies are held. Only a faithful delegating decorator (e.g. a counting/timing wrapper around `MemoryIndex`) is safe to inject — a *reshaping* index changes write semantics (what a versioned `put` treats as current, what cap-cull evicts), not just what reads return. A `null` index is treated as absent, same as every sibling optional param.

**Retrieval.** `IMemoryRetriever` + `IMemoryQuery` carrying `semantic?` / `asOf?` present-but-optional plus capability flags — **stable against a future semantic / temporal backend with no resignature**. Ships `RecencyRetriever` / `TagRetriever` / `StructuredFilterRetriever` / `LinkTraversalRetriever` (bounded, cycle-safe BFS over the derived backlink index) + `HybridRetriever` (capability-union, injectable `IMergeStrategy`); `SemanticRetriever` **degrades loudly** (`Result.fail`) until an `IVectorIndex` is wired. **Fragment-granular (sub-document) retrieval** ships alongside the record-granular path (N-Ask5): the **`IFragmentVectorIndex`** seam is a *sibling* of `IVectorIndex` (NOT a subtype — an index keyed by `(target, locator)` has no well-defined single-vector `add`) exposing `addFragments` (whole-record-replace) / `remove` / `query(vector, topK, maxPerRecord?)`; **`IVectorQueryHit`** carries two additive optional identity fields, **`locator?`** (an *advisory* `[start, end)` span — the region of the body a fragment was derived from, **NOT** a slice guaranteed to reproduce its text, since a rewriting segmenter may not leave the fragment as a substring at all) and **`fragmentId?`** (an opaque consumer-minted bytestring, stored and returned verbatim, never parsed, never in the query path). The same pair is optional on **`IEmbeddedFragment`**, where **at least one of the two is required** — enforced by **`embeddedFragmentConverter`** (and re-checked by both index impls), deliberately *not* by a conditional-required union. **No single field discriminates a fragment hit from a record hit, and the disjunction is not offered as a discriminator either** — fragment-ness is determined by *which index produced the hit* (`IFragmentVectorIndex.query` vs `IVectorIndex.query`); note `locator` absence now means either "record-granular hit" or "fragment with no honest span". Fragment-id stability across re-embeds is the **consumer's** responsibility (whole-record-replace re-emits the whole set); the library's guarantee is only "we never parse it". **`FragmentEmbedder`** is the chunk-and-embed sibling of `MemoryEmbedder`; **`InMemoryFragmentCosineIndex`** is the brute-force in-package impl; and **`FragmentSemanticRetriever`** is the discovery-half retriever that returns per-fragment `IVectorQueryHit`s (`{ target, locator, score }`) rather than records — so it is deliberately **NOT** an `IMemoryRetriever` (memory recall stays record-granular; sub-document knowledge uses the distinct fragment index) and degrades loudly when unwired. The store's additive **`fragmentIndex?` / `fragmentEmbedder?`** create params wire best-effort fragment-embed-on-write + removal on delete/eviction, independent of (and composable with) the record-vector `vectorIndex` / `embed` pair. `maxPerRecord` is applied during selection, before the topK cut. **Observe.** `MemoryObservationStore` (ring-backed via `RetainingRingBuffer`; schema-aware `query`; the store fires `read` / `write` / `delete` observations when `observers` are wired, zero overhead otherwise).

**Ingest (L3).** `MemoryIngestOrchestrator.create({ store, registry, codecs?, classifier, extractor, relationExtractor, entityResolver?, vectorIndex?, embed?, similarityThreshold?, similarityTopK?, cycleGuard?, logger? })` → `IMemoryIngestOrchestrator` (`ingestItem` / `ingestBatch`). Six stages, host callbacks at classify / extract / resolve / relate and fgv-owned everything else: a typed body-validation boundary (no unchecked host body reaches the store), two-layer stage-4 dedup, stage-5 edge validation + a global-acyclicity cycle guard, provenance stamping, and the contradicts→temporal interlock. Every host callback is wrapped so a throw or rejection becomes a `Result.fail`. **Stage-4 layer 1** is fgv's deterministic exact `{ kind, body }` match and **honors the kind's `dedupScope`** — `'content'` matches scope-wide cross-id, `'entity'` matches only at the candidate's own entity address — read through `IMemoryStore.dedupScopeFor(kind)` so the ingest path and the store's own write path can never disagree. **Stage-4 layer 2** (only when `entityResolver` + `vectorIndex` + `embed` are all wired) embeds the candidate, surfaces over-threshold neighbors, and dispatches to the host `IEntityResolver`. A **`duplicate-of` verdict redirects sibling edges** built against the collapsed candidate onto the record it collapsed into, rather than orphaning them into a whole-item ingest failure. See `.claude/project/agent-memory-ingest-design.md` for the stage pipeline, both dedup layers, the verdict → write mapping, and the cycle guard.

**Agent tools (L2).** `createMemoryTools({ store, retriever, registry, codecs, tools?, ... })` → `ReadonlyArray<AiAssist.IAiClientTool>` — the `memory_write` / `memory_read` / `memory_search` / `memory_context` / `memory_delete` suite over a wired store + retriever, ready to hand to an LLM tool loop (`DEFAULT_MEMORY_TOOLS` is search + context).

**Shipped (v1):** the full substrate above (knowledge + experience kind families) **plus operational semantic recall** — `InMemoryCosineIndex` (brute-force in-package cosine `IVectorIndex`) + embed-on-write (consumer-injected embedder; the core stays embedder-agnostic — no `ai-assist` import) **plus fragment-granular (sub-document) retrieval** — `IFragmentVectorIndex` + `InMemoryFragmentCosineIndex` + `FragmentSemanticRetriever` + fragment-embed-on-write (N-Ask5; the durable backend `SqliteVecFragmentIndex` ships in `@fgv/ts-agent-memory-sqlite-vec`) **plus the temporal versioned write path + temporal retrievers** (`TemporalVersionedPolicy` invalidate-don't-delete, `TemporalIdentityCodec`, `CurrentValidRetriever` / `AsOfRetriever` / `HistoryRetriever`), **the L2 agent-tool surface**, and **the L3 ingest orchestrator** — the last three previously listed here as pending fast-follows, corrected 2026-08 after verifying against source. **There are no outstanding fast-follows.** **Use this for any agent memory / knowledge vault — do not hand-roll a record store, content-hash dedup, or backlink index.** First consumer: PersonAIlity (knowledge-first, behind its `IKnowledgeSearchProvider`).

### `@fgv/ts-agent-memory-sqlite-vec` — persistent `IVectorIndex` + `IFragmentVectorIndex` (Node)
[libraries/ts-agent-memory-sqlite-vec](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-agent-memory-sqlite-vec)

`SqliteVecVectorIndex` — the **durable** counterpart to `InMemoryCosineIndex`: a Result-integration boundary over `better-sqlite3` + `sqlite-vec` that implements `@fgv/ts-agent-memory`'s `IVectorIndex` seam against a SQLite `vec0` file. Embeddings **persist across process restarts**, so a reopened vault answers queries with **no re-embedding** — closing the "re-embed the whole vault on every open" cost of the in-memory index at v2 scale. `SqliteVecVectorIndex.create({ database })` takes a consumer-owned `better-sqlite3` `Database` (BYO; the index never opens/closes it), loads the `sqlite-vec` extension, and recovers the established dimension from the existing table on reopen. Keyed on `edgeTargetKey` (`(scope, id)` — collision-proof across scopes), cosine similarity (`score = 1 − cosineDistance`, **byte-identical scoring to `InMemoryCosineIndex`**), replace via delete-then-insert (vec0 rejects `INSERT OR REPLACE`). **Drop-in swap with zero core change** — wire it as the store's `vectorIndex` and skip the consumer-opt-in `rebuild(asRecordSource())` on open. `better-sqlite3` / `sqlite-vec` are **peer dependencies**. **NOT in scope:** ANN/large-N indexing (brute-force `vec0` KNN, same regime as the in-memory index), connection lifecycle, embedding, a browser sibling. **Use this to back `FileTreeMemoryStore` when embeddings must survive a restart; use `InMemoryCosineIndex` for ephemeral / small vaults.**

`SqliteVecFragmentIndex` — the **durable** counterpart to `InMemoryFragmentCosineIndex`, and the fragment-granular sibling of `SqliteVecVectorIndex` in the same package (N-Ask5, #562). Implements `@fgv/ts-agent-memory`'s `IFragmentVectorIndex` seam against a `vec0` table keyed on `target_key` as a **`PARTITION KEY`** (many rows per record) with each fragment's identity in `+start_off` / `+end_off` / `+fragment_id` **auxiliary columns** (read back on query, never filtered — `fragment_id` in particular is stored and returned verbatim and is never parsed). `addFragments` is whole-record-replace (atomic delete-then-insert transaction), `remove` drops every fragment of a target, and `query(vector, topK, maxPerRecord?)` applies the per-record cap during selection before the topK cut — **byte-identical semantics + cosine scoring to `InMemoryFragmentCosineIndex`**, with the same reopen dimension recovery so a persistent fragment index answers with **no re-embedding on open**. `SqliteVecFragmentIndex.create({ database, tableName? })` (default table `'memory_fragments'`, distinct from the record index's `'memory_vectors'`; both may share one file). Locator offsets are validated as safe integers on write and coerced on read (safe-integer-mode-tolerant); an absent locator persists as a NULL offset pair, and a half-NULL pair (or a row with neither identity) fails the query loudly as corrupt persisted data. **Use this to back `FileTreeMemoryStore`'s `fragmentIndex` when sub-document fragment embeddings must survive a restart.**

**`vec0` schema changes require a drop-and-re-index — there are no in-place migrations.** `CREATE VIRTUAL TABLE IF NOT EXISTS` is a no-op against an existing table (SQLite never compares schemas) and `vec0` has no `ALTER TABLE ADD COLUMN`, so a table written by an earlier release of this package survives an upgrade untouched. When a release changes a table's columns, consumers must `DROP TABLE` (or point the index at a fresh `tableName`) and re-index. `SqliteVecFragmentIndex.create` detects the mismatch up front by parsing the stored `CREATE VIRTUAL TABLE` SQL and fails with an actionable message naming expected-vs-found columns, rather than letting an opaque `no such column` surface at statement-prepare time. **The cost is embedding time, never data** — vectors are derived artifacts; the vault records remain the source of truth. Known instance: the release that added `IEmbeddedFragment.fragmentId` added the `+fragment_id` column to the fragment table (the record table is unchanged).

## Application shells (React)

### `@fgv/ts-app-shell` — shared React app-shell primitives
[libraries/ts-app-shell](https://github.com/ErikFortune/fgv/tree/release/libraries/ts-app-shell)

Reusable React shell components: top bar, sidebar, column cascade, modal, keyboard registry, responsive layout, theme, drop-zone, and the **`messages` packlet** (toast + collapsible log panel + observability bridge).

**Messages — two-axis model.** A message separates the **filter axis** from the **display axis**:
- **`IMessage.level: MessageLogLevel`** (`'quiet'|'detail'|'info'|'warning'|'error'`, from `@fgv/ts-utils`) — the canonical log level, and the **only** thing filtering keys off. The status-bar filter threshold is a `ReporterLogLevel` and the predicate is `Logging.shouldLog(message.level, threshold)`, so the panel filters at the same granularity a ts-utils logger records — including `detail`. (`quiet` is only visible under the `all` threshold, per `shouldLog` semantics.)
- **`IMessage.severity?: MessageSeverity`** (`'info'|'success'|'warning'|'error'`) — an optional **styling-only** override (color / icon / toast). When absent, styling is derived from the level via **`deriveSeverityFromLevel(level)`** (`quiet`/`detail`/`info`→`'info'`, `warning`→`'warning'`, `error`→`'error'`). `'success'` is a UI affordance with no log-level analog — it lives only on this axis and is **never** derived; set it explicitly (e.g. a green "saved!" toast).

Create messages level-first: **`createMessage(level, text, options?)`** / **`addMessage(level, text, options?)`** where `options?: ICreateMessageOptions` carries `{ severity?, action? }`. The **`MessagesLogger`** / **`useLogReporter`** bridge implements the ts-utils `ILogger`/`LogReporter` interface and sets `level` straight through from the log call (lossless — `RetainingLogger` levels map 1:1), leaving `severity` undefined so display styling is derived. `DEFAULT_TOAST_CONFIG` stays keyed by the styling `MessageSeverity`. **Import `MessageLogLevel`/`ReporterLogLevel`/`shouldLog` from `@fgv/ts-utils`** — the messages packlet does not re-export them.

**Self-diagnosing setup.** `MessagesProvider` self-diagnoses missing Tailwind content-path setup via an in-panel warning message on mount — a one-shot probe measures whether a sentinel arbitrary-value utility (`h-[7.3215px]`, chosen to be vanishingly unlikely to appear in any consumer's source so it can only be generated by Tailwind scanning ts-app-shell's built JS via the content glob) resolves to a sized element, and if it does not, appends a `'warning'` message with an `action.href` linking to the README setup section. Idempotent under React.StrictMode double-render and HMR; always-on (not dev-only). `IMessageAction` is a discriminated union (`IMessageHrefAction | IMessageCallbackAction`) — exactly one of `href` (external link) or `onAction` (callback) is required at the type level.

**`StatusBar` layout props.** The collapsible log panel takes **`maxExpandedHeight?: string`** (CSS length, default `'40vh'`) — the expanded panel is bounded to this height on both desktop and mobile, with the message list scrolling within the bound while the header/filter controls stay fixed; the mobile expanded view is an in-flow bounded sheet (with a dimming backdrop for tap-to-dismiss), not a `fixed inset-0` viewport takeover. **`defaultExpanded?: boolean`** (default `false`) controls expanded-on-mount. A discoverable collapse control (`✕`) sits in the expanded header on both layouts.

The three tier keys are the **only** completion-model selectors; `image`/`embedding` select the non-completion modalities. **Cascade:** a tier request walks an ordered fallback list and takes the first key present — `frontier → advanced → base`, `advanced → base`, `base` — so a provider only declares the tiers it differentiates (OpenAI wires all three — `frontier` → `gpt-5.6-sol`, which works on Chat Completions; Anthropic, Gemini, and xAI omit `frontier` and cascade to their `advanced` model; the previous frontier target `gpt-5.5-pro` is Responses-API-only and stays `modelOverride`-only). `base` is the required floor and universal fallback; `image`/`embedding` keep flat `modality → base` behavior. **Composition, not competition:** thinking (reasoning effort) and tools (server-side tools) are orthogonal request/capability params — they ride on top of whatever model the tier picked and **never select a model** (`ModelSpecKey` carries no `thinking`/`tools` keys — they were removed when the tier axis landed). `tier: 'base'` + a thinking config resolves the cheap base model and sends the thinking param to it; every base model is thinking-capable, so thinking composes with any tier with zero capability checks. The alias layer covers **selection/default churn only** — capability-detection `idPattern` rules and the typed `*ModelNames` unions remain manual axes (see TECH_DEBT). **Every turn entry point takes the unified `{ system?, messages: IChatMessage[] }` request shape (`IChatRequest`)** — `messages` is the ordered conversation, the last entry is the current user turn and the preceding entries are history; history is always linearized before the current turn (no head/tail asymmetry). `AiPrompt.toRequest()` lowers a system+user prompt to this shape. The proxy wire body serializes `{ system?, messages }`. **For JSON-shaped completions use `generateJsonCompletion<T>({ converter, ... })`** — it appends a smart "raw JSON only" prompt hint and runs the response through `fencedStringifiedJson`, which strips Markdown fences, leading preamble, and trailing prose before validating with the caller's `Converter<T>` or `Validator<T>`. The bare `extractJsonText` helper is exported for callers that just need wrapper-stripping; `fencedStringifiedJson({ extractor, inner })` is the extension point for custom extractors. **Don't reimplement fence-stripping in consumers.** **To find out *why* a JSON-shaped response failed to parse** (not just that it did), use `classifyJsonParseFailure(text)` → `JsonParseFailureReason` — a structural classifier (walks the JSON grammar; never regex-matches the engine's `JSON.parse` error string, so verdicts don't drift across Node/V8 versions) that names four property-name-position faults with `token` + `offset` (0-based into the original `text`, not the extracted substring): `unquoted-property-name`, `single-quoted-property-name`, `unterminated-property-name`, `elided-member`; everything else — including truncation, missing colons, and bad number literals — falls to the conservative `'unknown'` rather than guessing. **Total**: non-string input returns `'unknown'` instead of throwing, matching `extractJsonText`'s guard. **For image generation use `callProviderImageGeneration`/`callProxiedImageGeneration`** — supports OpenAI DALL-E 3 / gpt-image-1 (`openai-images`), xAI grok-imagine generations (`xai-images`) and edits (`xai-images-edits`), and Gemini image-output via generateContent (`gemini-image-out`). The layered options system provides top-level keys (`size`, `quality`, `seed`, `count`) alongside per-provider `models` blocks for provider-specific params (e.g. `{ provider: 'openai', family: 'gpt-image', config: { outputFormat, background, moderation, outputCompression } }`). Provider capability is declared on `IAiProviderDescriptor.imageGeneration: IAiImageModelCapability[]`; `imageOptionsResolver` translates the layered options into a wire-ready `IResolvedImageOptions`. **For harness-side client tools (tools the caller implements, not the provider) use `executeClientToolTurn`** — the single-turn helper for tool-use conversations. Supply `clientTools: IAiClientTool[]` alongside any `tools: IAiServerToolConfig[]`; the helper returns `{ events: AsyncIterable<IAiStreamEvent>, nextTurn: Promise<Result<IAiClientToolTurnResult>> }` where `events` streams intermediate tool events and `nextTurn` awaits the complete round-trip result (including `continuation.messages` — the provider-format wire messages to re-supply on the next turn). `IAiClientTool` carries `config: IAiClientToolConfig` (name, description, `parametersSchema: ISchemaValidator<TParams>` — use `JsonSchema.object(...)` from `@fgv/ts-json-base`) and `execute: (args: unknown) => Promise<Result<unknown>>`. Type the tool as `IAiClientTool` (unparameterized, default `unknown`) and validate args inside `execute` via `parametersSchema.validate(args)` — the `execute` callback is contravariant in `TParams` so a typed `IAiClientTool<{key:string}>` is not assignable to `IAiClientTool<unknown>`. For multi-turn conversations pass `continuationMessages: continuation.messages` (type `ReadonlyArray<JsonObject>`) — `continuation.messages` is **cumulative** (replace each round, do not manually concatenate; the library prepends the inbound tail automatically so the array always covers all rounds so far) — these are provider-format wire objects appended after the current user turn. The exact wire-shape handling is per-provider: **Anthropic** projects each entry to `{ role, content }` (extra fields dropped; invalid entries skipped); **Gemini** projects to `{ role, parts }` (same shape guard); **OpenAI Responses / xAI** pass entries through verbatim with a `JsonObject` guard (since OpenAI Responses items are a `type`-keyed discriminated union whose fields differ per item). Consumers should not assume arbitrary fields round-trip on every provider — the high-fidelity round-trip is on the OpenAI/xAI path; Anthropic and Gemini preserve only the projected fields. Cross-provider continuation works on **all four providers**. **Do not put continuation wire objects in `messages`** (the unified `IChatRequest` conversation turns) — `continuationMessages` is a distinct post-current-turn axis whose provider-native fields the normalized `messages` path would strip. `IResolvedThinkingConfig` is exported from the packlet for callers that pre-resolve thinking options (e.g. `{ anthropicEffort: 'low' }`) and pass them directly to `executeClientToolTurn`. **Tool parameters authored as `JsonSchema.object(...)` work transparently on Gemini** — the adapter sanitizes draft-07-only keywords (`additionalProperties`, `$schema`) recursively before submission, so strict-by-default schemas don't need consumer pre-processing. **Gemini API constraint:** Gemini's `generateContent` forbids combining built-in grounding (`web_search`) with function calling in the same request — pick one or the request HTTP 400s with `INVALID_ARGUMENT`. **Completion diagnostic:** `IAiStreamDone.incompleteReason?: string` (`@public`) carries the OpenAI/xAI Responses `incomplete_details.reason` (`'max_output_tokens'`, `'content_filter'`, …) when `truncated === true`; absent when the stream completed normally. **Provider-drift instrumentation:** Anthropic and OpenAI Responses adapters maintain a `RECOGNIZED_*_EVENTS` allowlist and log a one-time `logger.warn` per stream per unrecognized SSE event name. Warning starts with the stable `ai-assist:unrecognized-event` tag (filter on this prefix to alert on provider-API evolution); includes a **default-safe structural payload preview** (top-level JSON keys + length — never field values) for triage; names the allowlist constant so a developer can find the right list to update. Production deployments wire the `ILogger` via the streaming-call params (`IProviderCompletionStreamParams.logger` / `IExecuteClientToolTurnParams.logger` — NOT via the per-adapter `IStreamApiConfig`, which carries only `{ baseUrl, apiKey, model }`); deployments that don't (default `NoOpLogger`) get a silent no-op. Ops triaging an active drift signal can opt in to the **raw payload preview** by setting `AI_ASSIST_UNRECOGNIZED_EVENT_FULL_PAYLOAD=1` in the environment — keep this off in production by default since SSE payloads can carry tool args / user-conversation text / other sensitive content. Gemini-side drift instrumentation is queued (JSON-chunk wire shape doesn't fit the SSE-event-name allowlist concept). **For embeddings (`text → vector`) use `callProviderEmbedding`/`callProxiedEmbedding`** — the cross-provider embedding primitive (third modality alongside completion and image generation). Batch in (`input: string \| string[]`), `number[][]` out, `Result`-wrapped. Two wire formats behind one dispatcher: `openai-embeddings` (`POST /embeddings`) serves **OpenAI** (`text-embedding-3-*`), **Ollama** (point `endpoint` at `http://localhost:11434/v1`), **openai-compat** self-hosted servers, and **Mistral** (`mistral-embed`); `gemini-embeddings` (`POST /models/{model}:batchEmbedContents`) serves **Google Gemini** (`gemini-embedding-001`) with its `taskType` retrieval-asymmetry knob. Capability is declared on `IAiProviderDescriptor.embedding: IAiEmbeddingModelCapability[]` (model-prefix matched, longest wins) and selects the model via the `embedding` `ModelSpecKey`. Knob handling (`dimensions`, `taskType`) is **no-op-where-unsupported, not a failure** — a caller passes `taskType: 'retrieval-query'` once and it maps to Gemini's wire `RETRIEVAL_QUERY` while being a logged no-op on the (symmetric) OpenAI-format providers, so the cross-provider call site never branches. Empty input short-circuits to an empty result with no wire call; a batch over the capability's `maxBatchSize` fails fast (no auto-chunking). xAI and Anthropic declare no embedding capability (no first-party endpoint) and reject up front. Vectors are `number[]` (not `Float32Array`) for JSON-wire fidelity — call `Float32Array.from(vector)` at the vector-store boundary; the library does not L2-normalize (Gemini MRL-truncated vectors may need it). |

**The headline win — `chatStructured` no-drift, grammar-constrained output.** `schema` is a `JsonSchema.ISchemaValidator<T>` (`JsonSchema.object(...)` from `@fgv/ts-json-base`). The SAME object is BOTH the wire `format` (`schema.toJson()`, draft-07-sanitized to strip `$schema`/`additionalProperties` per the Gemini precedent) AND the reply validator (`schema.validate()`) — they cannot drift. `T` is derived via `JsonSchema.Static<typeof schema>` — no caller-supplied `T`, no cast. Ollama constrains the token sampler to the schema, so the reply is structurally guaranteed to match (a stronger guarantee than ai-assist's prompt-and-parse `generateJsonCompletion`, which asks-and-parses). `chatStructured` runs over the streaming chat path internally (the only path the `ollama` lib lets an `AbortSignal` cancel) and validates the assembled document whole.

**Dependency posture (mirrors `@fgv/ts-extras-transformers`):** `ollama` is a **peer + dev** dependency (bring your own pinned version); `@fgv/ts-utils` is **peer + dev** (consumer-provided, not installed transitively); only `@fgv/ts-json-base` is a hard **dependency** (`chatStructured` consumes `JsonSchema` as a first-class surface type).

**Explicitly NOT in scope:** text completion / chat / streaming (ai-assist via `/v1`); browser / CORS (`ollama/browser` + `OLLAMA_ORIGINS` — a future `@fgv/ts-web-extras-ollama` sibling); model authoring (`push`/`create`/`copy`); `keep_alive`/lifecycle policy (pass-through only); pull-progress UI; multi-host orchestration / pooling / retries; native tool-calling on `/api/chat` (ai-assist owns tool turns). **Native embeddings (`embed`) are CUT** — resolved by the `ai-assist-embeddings` design (OQ-1): Ollama embeddings are reachable via `/v1/embeddings` and are owned by `AiAssist.callProviderEmbedding` (the `ollama` descriptor's `baseUrl` already targets `http://localhost:11434/v1` — pass the embedding model via `modelOverride`, and use the per-call `endpoint` override for a non-default host). Native `/api/embed` adds only marginal diagnostics (`total_duration`/`prompt_eval_count`) not worth a parallel path; revisit additively only if a concrete consumer needs them.

**Upstream:** `ollama` `^0.6.0` (peer dependency).

### Result-integration boundary — package shape convention

When fgv wants to expose functionality from a well-maintained upstream library without baking in opinion or maintenance burden, the right shape is a thin **Result-integration boundary**: convert thrown exceptions / rejected promises into `Result<T>`, expose ~5–8 primitive operations, and enumerate explicitly what is NOT in scope. No opinionated orchestration beyond the conversion.

Reference instances in this file:
- **`@fgv/ts-extras-webauthn` + `@fgv/ts-web-extras-webauthn`** — six primitives wrapping `@simplewebauthn/*`; ceremony orchestration, challenge management, and credential storage are explicitly out of scope.
- **`@fgv/ts-extras-transformers` + `@fgv/ts-web-extras-transformers`** — four primitives wrapping `@huggingface/transformers`; pipeline cache, model registry, device/quantization policy are explicitly out of scope.
- **`@fgv/ts-extras-mcp`** — seven primitives wrapping `@modelcontextprotocol/sdk` plus one piece of glue (`adaptMcpTools` → `AiAssist.IAiClientTool[]`); browser sibling, MCP resources/prompts/sampling, OAuth, and multimodal passthrough are explicitly out of scope.
- **`@fgv/ts-extras-ollama`** — six primitives (v0.1; native `embed` cut — Ollama embeddings are owned by `AiAssist.callProviderEmbedding` via `/v1`) wrapping the `ollama` JS lib's *native* API (model management, streamed pull, grammar-constrained structured output); the completion path (ai-assist via `/v1`), browser/CORS, and model authoring are explicitly out of scope.
- **`@fgv/ts-agent-memory-sqlite-vec`** — `SqliteVecVectorIndex` **and** `SqliteVecFragmentIndex` wrapping `better-sqlite3` + `sqlite-vec` to implement `@fgv/ts-agent-memory`'s `IVectorIndex` **and `IFragmentVectorIndex`** seams with a persistent `vec0` file (survives restart → no re-embed on open); ANN/large-N, connection lifecycle, embedding, and a browser sibling are explicitly out of scope. Note this one implements existing *fgv* seams (rather than only wrapping the upstream lib), so its "primitives" are the `IVectorIndex` / `IFragmentVectorIndex` methods plus each `create`.

Both pairs have an explicit "NOT in scope" enumeration — that list is load-bearing. A new integration-boundary package should carry the same shape: thin conversion + explicit not-in-scope list + no opinion added. See the WebAuthn pair's README as the prose template.

## Decision shortcuts (start here)

- **Error handling / fallible function?** → `Result<T>` from `@fgv/ts-utils/base`. Never throw across module boundaries.
- **Validating untyped JSON / config input?** → `Converters.object` from `@fgv/ts-utils/conversion` or `@fgv/ts-json-base/converters`. Never write `typeof x === 'object' && ... as T`.
- **Validating an existing class instance?** → `Validators` from `@fgv/ts-utils/validation`.
- **Map/collection with validation?** → `ResultMap` / `Collector` family from `@fgv/ts-utils/collections`.
- **Need a bounded most-recent-N ring of records with monotonic `seq` cursor paging, predicate filtering, and `lastSeq` preserved across `clear()`?** → `RetainingRingBuffer<T extends { seq: number }>` from `@fgv/ts-utils/collections`. A *pure* storage substrate — the caller mints each record (assigning its own `seq` / `timestamp`); the buffer only retains / evicts / queries (`query({ sinceSeq?, limit?, filter? })`). Use it as the shared mechanism beneath any "retain the most recent N records, page by cursor, filter" surface (observation stores, structured-log rings) instead of hand-rolling a circular buffer.
- **Aggregating multiple errors?** → `MessageAggregator` + `mapResults` from `@fgv/ts-utils/base`.
- **N independent async `Result`-returning operations, with a concurrency bound?** → the **async `Result` family** in `@fgv/ts-utils/base`: `mapResultsAsync` / `mapDetailedResultsAsync` / `mapSuccessAsync` / `mapFailuresAsync` / `allSucceedAsync`. Same names, parameter order and folds as their sync siblings; add `{ concurrency }` (`IAsyncResultOptions`, defaulting to the exported finite `DEFAULT_RESULT_CONCURRENCY`) to bound in-flight work. **You cannot pass `Promise<Result<T>>[]` — and that is the whole point.** By the time a promise exists its operation has already started, so a collector handed materialized promises has nothing left to bound; every async member therefore takes *deferred* work. Two forms: **thunks** (`mapResultsAsync(work: Iterable<AsyncDeferredResult<T>>, options?)`) for N *different* operations or heterogeneous fan-out, and **`(items, fn)`** (`mapResultsAsync(items, (item, index) => Promise<Result<T>>, options?)`) for N applications of *one* operation — the `(items, fn)` form is the one to reach for when you want the mistake to be unsayable. Results come back **in input order**, not completion order. **Don't hand-roll `await Promise.all(xs.map(f))` + `mapResults`** — that is `mapResultsAsync` with unbounded concurrency spelled out longhand.
- **Async operation that is *serial by contract*, not a fan-out?** → `populateObjectAsync` (keyed heterogeneous object; each initializer sees the `Partial<T>` populated before it — dependency sequencing) or `firstSuccessAsync` (ordered fallback: try each candidate in turn, stop at the first success — e.g. a local override before a default, or a search path in precedence order). Both are **transitively async** — the algorithm is the sync one, only the primitives it calls are async — so both take an optional `IMessageAggregator` and, deliberately, **no `IAsyncResultOptions`**: a `concurrency` field on a serial-by-definition operation would be a lie in the type signature. Reach for these instead of a hand-rolled `for`/`await` loop that forgets to aggregate the failed attempts.
- **Reading files (Node, browser, or zip)?** → `FileTree` from `@fgv/ts-json-base/file-tree` (+ `ts-extras/zip-file-tree` or `ts-web-extras/file-tree` for the backend).
- **Loading/saving JSON files?** → `JsonFsHelper` from `@fgv/ts-json-base/json-file`.
- **JSON templating or conditional inclusion?** → `JsonConverter` from `@fgv/ts-json/converters`.
- **Deep-merging JSON?** → `JsonEditor.mergeObjectInPlace` from `@fgv/ts-json/editor`.
- **Diffing JSON?** → `@fgv/ts-json/diff`.
- **Branded ID type?** → `Brand<T>` from `@fgv/ts-utils/base`.
- **Generating a UUID?** → `generateUuid()` from `@fgv/ts-utils/base` for the call-site one-liner; `ICryptoProvider.generateUuid()` from `@fgv/ts-extras/crypto-utils` when you already hold a provider or want a deterministic test override. Never call `globalThis.crypto.randomUUID()` directly.
- **Hashing / canonical hash of an object?** → `Crc32Normalizer` (`ts-utils/hash`) or `Md5Normalizer` (`ts-extras/hash` / `ts-web-extras/crypto-utils`).
- **Symmetric encryption / decryption (AES-GCM)?** → `DirectEncryptionProvider` or `KeyStore.encryptByName` from `@fgv/ts-extras/crypto-utils`, backed by `NodeCryptoProvider` (Node) or `BrowserCryptoProvider` (browser).
- **Need AES-256-GCM encrypt/decrypt with a key you already hold (PBKDF2/HKDF output, raw bytes)?** → `ICryptoProvider.encrypt(plaintext, key)` / `ICryptoProvider.decrypt(data, key, iv, authTag)` from `@fgv/ts-extras/crypto-utils`. The higher-level `DirectEncryptionProvider` and `KeyStore.encryptByName` paths wrap these for named-key lookup workflows.
- **Password-protected vault for keys / API keys / keypairs?** → `KeyStore` from `@fgv/ts-extras/crypto-utils`. Use `addSecretFromPassword` to derive + store, `verifySecretFromPassword` for constant-time password verification.
- **Need a private-key storage backend so `KeyStore.addKeyPair` works?** → **Node:** `CryptoUtils.KeyStore.EncryptedFilePrivateKeyStorage.create({ directory, encryptionKey, cryptoProvider })` — import `CryptoUtils` from `@fgv/ts-extras` (or the `@fgv/ts-extras/crypto` subpath); one AES-256-GCM-encrypted JWK file per key via FileTree; you supply the 32-byte `encryptionKey`; `supportsNonExtractable: false`. **Browser:** `CryptoUtils.IdbPrivateKeyStorage.create({ databaseName?, storeName? })` — import `CryptoUtils` from `@fgv/ts-web-extras` (IndexedDB; stores `CryptoKey` directly; `supportsNonExtractable: true`). Pass the instance as `KeyStore.create({ ..., privateKeyStorage })`. Don't roll your own `IPrivateKeyStorage`.
- **PBKDF2 key derivation, ECIES wrap/unwrap, asymmetric keypairs (Ed25519, ECDSA-P256, ECDH-P256, RSA-OAEP, X25519)?** → `ICryptoProvider` from `@fgv/ts-extras/crypto-utils`. Never call `node:crypto` or `crypto.subtle` directly.
- **Need to hash / verify a password (PBKDF2)?** → `KeyStore.addSecretFromPassword` / `verifySecretFromPassword` from `@fgv/ts-extras/crypto-utils`. Never roll PBKDF2 directly.
- **Need to hash / verify a password with Argon2id?** → `KeyStore.addSecretFromPasswordArgon2id` / `verifySecretFromPasswordArgon2id` from `@fgv/ts-extras/crypto-utils`, passing a `NodeArgon2Provider` (`@fgv/ts-extras-argon2`) or `BrowserArgon2Provider` (`@fgv/ts-web-extras-argon2`). Use `ARGON2ID_OWASP_MIN` or `ARGON2ID_PASSPHRASE` presets from `CryptoUtils` for OWASP-compliant parameters.
- **Need an Argon2id provider (Node)?** → `NodeArgon2Provider.create()` from `@fgv/ts-extras-argon2`.
- **Need an Argon2id provider (browser / WASM)?** → `BrowserArgon2Provider.create()` from `@fgv/ts-web-extras-argon2`.
- **Need stable canonical JSON (RFC 8785)?** → `Normalizer.canonicalize()` (available on `HashingNormalizer`, `Crc32Normalizer`, or any `Normalizer` subclass) from `@fgv/ts-utils` hash packlet.
- **Need to encode/decode a public key as multibase SPKI?** → `exportPublicKeyAsMultibaseSpki(key, provider)` / `importPublicKeyFromMultibaseSpki(encoded, algorithm, provider)` from `@fgv/ts-extras/crypto-utils`. Pass the `ICryptoProvider` instance so the underlying SPKI export/import routes through the correct platform implementation.
- **Need hybrid public-key encryption (encrypt to a recipient's public key, one-shot)?** → `HpkeProvider` from `@fgv/ts-extras/crypto-utils` (Node) or `@fgv/ts-web-extras` (browser). `HpkeProvider.create(subtle).orThrow()` then `sealBase(recipientPub, info, aad, plaintext)` / `openBase(recipientPriv, info, aad, enc, ciphertext)`. Suite: DHKEM(X25519, HKDF-SHA256) + HKDF-SHA256 + AES-256-GCM (RFC 9180 base mode). `info` is mandatory and must be application-specific context bytes — empty `info` provides no context binding. Use `HpkeProvider.encodeEnvelope` / `decodeEnvelope` for wire transport. Never roll your own KEM.
- **Need standalone HKDF-SHA256 key derivation?** → `HpkeProvider.create(subtle).orThrow().hkdf(secret, salt, info, length)` from `@fgv/ts-extras/crypto-utils` (or `@fgv/ts-web-extras` for browser). Raw RFC 5869 HKDF — unlabeled, suitable for application-level key derivation.
- **Need X25519 key agreement?** → `generateKeyPair('x25519', ...)` from `ICryptoProvider` (`@fgv/ts-extras/crypto-utils`) to produce the keypair; use `ICryptoProvider.exportPublicKeySpki` / `importPublicKeySpki` to exchange public keys. Raw `deriveBits` for the shared secret is not yet wrapped by `ICryptoProvider` — do not call `crypto.subtle` directly.
- **Need to sign data or verify a signature (Ed25519, ECDSA-P256)?** → `ICryptoProvider.sign(privateKey, data)` / `ICryptoProvider.verify(publicKey, signature, data)` from `@fgv/ts-extras/crypto-utils`. Algorithm is inferred from the key's `algorithm` property — generate keys with `generateKeyPair('ed25519', ...)` or `generateKeyPair('ecdsa-p256', ...)`. Both return `Promise<Result<...>>`.
- **Need HMAC-SHA256 authentication / MAC verification?** → `ICryptoProvider.hmacSha256(key, data)` / `ICryptoProvider.verifyHmacSha256(key, signature, data)` from `@fgv/ts-extras/crypto-utils`. The verify variant uses `timingSafeEqual` internally for constant-time comparison. Both return `Promise<Result<...>>`.
- **Need constant-time byte comparison?** → `ICryptoProvider.timingSafeEqual(a, b)` from `@fgv/ts-extras/crypto-utils`. Returns `boolean` directly (not `Result`). Node impl delegates to `crypto.timingSafeEqual`; browser impl uses XOR-walk accumulator. Never use `===` or loop with early return for security-sensitive comparisons.
- **Parsing a JSON-shaped string (with optional inner validation)?** → `Converters.stringifiedJson(inner?)` from `@fgv/ts-json-base/converters`.
- **Need typed JSON Schema for LLM tool authoring (one declaration → derived type + validator + wire schema)?** → `JsonSchema` from `@fgv/ts-json-base`. Author with `JsonSchema.object({ ... })` (factories: `string`/`number`/`integer`/`boolean`/`enumOf`/`array`/`object` + the `optional` modifier); `JsonSchema.Static<typeof schema>` derives the static type with no assertion; **the schema IS a Validator** — call `schema.validate(input)` directly (no separate `toConverter` step); `schema.toJson()` gives the draft-07 wire schema for the provider's tool `parameters`; `JsonSchema.fromJson(raw)` parses an MCP-discovered `JsonObject` into an opaque `ISchemaValidator<JsonValue>` for runtime validation. **Don't author a schema and a separate Validator for the same shape — they are the same object and cannot drift.** Strict numeric + strict object are the defaults (LLM convention). LLM-tool subset only (no `$ref`/`oneOf`/`pattern`/custom formats).
- **Asking an LLM for JSON and getting a validated `T`?** → `AiAssist.generateJsonCompletion<T>({ converter, ... })` from `@fgv/ts-extras/ai-assist`. Tolerates Markdown fences, preamble, and trailing prose by default. Don't reimplement fence-stripping in consumers.
- **Running a tool-use conversation with harness-side client tools?** → `AiAssist.executeClientToolTurn({ descriptor, apiKey, system?, messages, clientTools, tools?, model?, resolvedThinking? })` from `@fgv/ts-extras/ai-assist`. Like every turn entry point it takes the unified `{ system?, messages }` request shape (the last `messages` entry is the current user turn; preceding entries are history). Returns `{ events, nextTurn }` — consumer drives the outer multi-turn loop. Pass `continuationMessages: continuation.messages` on subsequent turns — `continuation.messages` is **cumulative** (replace each round, do not manually concatenate); do NOT put continuation wire objects in `messages` (they are a distinct post-current-turn axis). Works on **all four providers** (Anthropic, OpenAI Responses, Gemini, xAI via OpenAI). Type client tools as `IAiClientTool` (unparameterized) and validate args inside `execute` — the callback is contravariant in `TParams`. Author the `parametersSchema` with `JsonSchema.object(...)` from `@fgv/ts-json-base`; `schema.validate(args)` is the round-trip verify step. **Gemini-specific:** cannot combine `web_search` (built-in grounding) with client tools in the same request — Gemini's API HTTP-400s on that combination; pick one.
- **Making an MCP server's tools callable from an ai-assist tool-use conversation?** → `@fgv/ts-extras-mcp` (Node). `connectMcpSession` → `adaptMcpTools(session, { logger })` → hand `result.tools` (`AiAssist.IAiClientTool[]`) to `AiAssist.executeClientToolTurn({ ..., clientTools: result.tools })`. `adaptMcpTools` gracefully degrades: tools whose `inputSchema` is outside the `JsonSchema.fromJson` subset land in `result.skipped` (name + JSON-pointer reason + raw schema) and NOISY-warn rather than failing the catalog. Transports: `createStdioTransport({ command, args })` (spawns a subprocess — trust boundary) or `createHttpTransport({ url, headers })`. Use the `samples/testbed` `mcp-probe` scenario (`MCP_PROBE_URL` / `MCP_PROBE_COMMAND`) to get a compatibility report for any server. **Don't hand-roll an MCP client or a JSON-Schema→client-tool adapter.**
- **Diagnosing an OpenAI/xAI Responses stream that completes empty?** → Check `IAiStreamDone.incompleteReason?: string` on the `done` event. `'max_output_tokens'` → reasoning + tools consumed the output budget (raise the cap or shorten the prompt); `'content_filter'` → safety filter blocked the response. Absent → stream completed normally; if you still see no text, pass an `ILogger` to the streaming call (`callProviderCompletionStream({ ..., logger })` or `executeClientToolTurn({ ..., logger })`) and look for `ai-assist:unrecognized-event` warns — the streaming adapter probably saw an event family it doesn't handle yet (provider-API evolution).
- **Alerting on provider-API evolution affecting `@fgv/ts-extras/ai-assist`?** → Pass an `ILogger` via the higher-level streaming params (`IProviderCompletionStreamParams.logger`, `IExecuteClientToolTurnParams.logger`, etc.) and filter on the stable `ai-assist:unrecognized-event` warn prefix. The streaming helpers thread the logger down to the per-adapter unknown-event sites; the per-adapter `IStreamApiConfig` itself is just `{ baseUrl, apiKey, model }` and is not where consumers wire the logger. The Anthropic and OpenAI Responses adapters maintain per-stream-dedup'd allowlists of recognized SSE event names; an unrecognized event triggers one warn per stream per name including a length-capped structural payload preview (top-level JSON keys + length by default; raw payload via the `AI_ASSIST_UNRECOGNIZED_EVENT_FULL_PAYLOAD` env var). Use this in production to alert when a provider's wire shape changes (likely class of issue: adapter parse miss → silent feature degradation). Gemini's drift instrumentation is queued separately (different wire shape).
- **Stripping LLM Markdown fences from raw text?** → `AiAssist.extractJsonText` (default extractor) or `AiAssist.fencedStringifiedJson({ extractor, inner })` (extension point) from `@fgv/ts-extras/ai-assist`.
- **Diagnosing *why* an LLM's JSON response failed to parse (not just that it did)?** → `AiAssist.classifyJsonParseFailure(text)` from `@fgv/ts-extras/ai-assist` — returns a typed `JsonParseFailureReason` (four named property-name-position faults with `token`/`offset`, else `'unknown'`); structural, not regex-on-engine-message; total (non-string input → `'unknown'`, never throws). Branch on the reason to repair the cheap cases, re-prompt the expensive ones, or fail outright — don't regex-match `JSON.parse`'s message.
- **Generating images from an LLM provider?** → `AiAssist.callProviderImageGeneration({ descriptor, apiKey, params })` from `@fgv/ts-extras/ai-assist`. Use `callProxiedImageGeneration(proxyUrl, ...)` to route through a proxy when direct browser calls are CORS-restricted. Pass top-level options (`size`, `quality`, `seed`, `count`) and a `models` array for provider-specific config blocks.
- **Declaring image generation capability on a provider?** → Add `imageGeneration: IAiImageModelCapability[]` to `IAiProviderDescriptor`. Each capability entry carries `format` (`'openai-images' | 'xai-images' | 'xai-images-edits' | 'gemini-image-out'`), `modelPrefix`, and optional flags like `acceptsImageReferenceInput`, `defaultOutputMimeType`, `outputParamStyle`, `supportsQualityParam`, `maxCount`.
- **Looking up a model's image/embedding capability by id?** → `AiAssist.resolveImageCapability`/`resolveEmbeddingCapability` from `@fgv/ts-extras/ai-assist`. Both resolve an `@alias` before prefix-matching, so pass either an alias or a concrete provider id — both resolve to the correct capability entry rather than an alias silently matching the provider's catch-all rule.
- **Enabling extended thinking / reasoning on LLM completions?** → Pass `thinking: IThinkingConfig` to `callProviderCompletion` or `callProviderCompletionStream`. `IThinkingConfig` supports a cross-provider generic `effort?: 'low' | 'medium' | 'high'` shorthand and an optional `providers[]` array for per-provider config blocks. Provider-specific types: `IAnthropicThinkingConfig` (effort), `IOpenAiThinkingConfig` (effort, including `'none'` to re-enable temperature), `IGeminiThinkingConfig` (thinkingBudget integer), `IXAiThinkingConfig` (effort). Model-specific and `'other'` escape-hatch blocks let you override for individual models without affecting others. Merge precedence: generic effort → provider-generic blocks → model-specific/other blocks (later declaration wins within a tier). **Temperature + thinking conflicts**: Anthropic and OpenAI (non-`'none'` effort) and xAI return `Result.fail`; Gemini accepts both. Thinking content is discarded in this phase; caller-visible thinking-event surfacing is the scope of the followup stream `ai-assist-thinking-events`. Unknown/unsupported providers silently ignore the `thinking` field.
- **Managing a local Ollama sidecar — listing / inspecting / pulling / deleting models, or grammar-constrained structured output?** → `@fgv/ts-extras-ollama` (Node-only). `createOllamaClient({ host? })` → `Result<IOllamaClient>`, then `listModels` / `listRunning` / `showModel` / `deleteModel` (model management the `/v1` layer can't express), `pullModel({ model, onProgress?, signal? })` (streamed download progress → terminal `Result`), and **`chatStructured<T>({ model, messages, schema, signal? })`** for grammar-constrained JSON: the `JsonSchema.object(...)` schema is BOTH the wire `format` (draft-07-sanitized) AND the `schema.validate()` reply validator — one declaration, no drift, `T` derived via `JsonSchema.Static`. **For text completion / streaming / tool-use against the same daemon, this is the WRONG package — use `@fgv/ts-extras/ai-assist` with a provider `endpoint` of `http://localhost:11434/v1`.** Native `embed` is **CUT** — Ollama embeddings are owned by `AiAssist.callProviderEmbedding` via `/v1/embeddings` (see the "text → vector" decision shortcut and OQ-1), not this package. `ollama` is a peer dependency.
- **Running a HuggingFace model locally (text classification / embeddings / summarization) with a Result boundary?** → `loadPipeline` + `classify` / `classifyAll` / `embed` / `summarize` from `@fgv/ts-extras-transformers` (Node) or `@fgv/ts-web-extras-transformers` (browser). Thin `Result`-wrapped facade over `@huggingface/transformers` — no caching/device/quantization policy (use the upstream lib directly for that). Use `classifyAll` when you need the full per-label vector (it bakes in `top_k: null`); `embed` returns the raw `Tensor` (pass `{ pooling: 'mean', normalize: true }` for a sentence vector). **In a browser bundle, keep your core facade-agnostic (inject the fn, type-only imports) and load the Node facade only via `import(/* webpackIgnore: true */ ...)` on the CLI path** — see the `samples/testbed` `local-classifier-safety` / `local-embedding-search` / `local-summarization` scenarios.
- **Summarizing text locally (cheap/fast, small model) vs. in the cloud?** → **local:** `summarize` from `@fgv/ts-extras-transformers` (e.g. `loadPipeline('summarization', 'Xenova/distilbart-cnn-6-6')`) — the cheap/fast/offline path for simple/medium inputs. **Cloud (quality on long/complex docs):** a completion via `@fgv/ts-extras/ai-assist`. The escalation policy (when to defer to the cloud) is the consumer's, not the facade's.
- **Need a text embedding (`text → vector`)?** Three paths; pick by where the weights run:
  - **In-process / local / offline (you own the model lifecycle)** — on-device RAG pre-filter, privacy-sensitive, zero per-call cost → `embed` / `loadPipeline('feature-extraction', …)` from **`@fgv/ts-extras-transformers`** (Node) or **`@fgv/ts-web-extras-transformers`** (browser). Returns a raw `Tensor` (pass `{ pooling: 'mean', normalize: true }` for a sentence vector). You manage model download / cache / device / quantization.
  - **Cross-provider cloud HTTP** — OpenAI `text-embedding-3-*`, Gemini `gemini-embedding-001`, Mistral `mistral-embed`, **or a self-hosted OpenAI-compatible / Ollama server via the `endpoint` override** → `AiAssist.callProviderEmbedding` from **`@fgv/ts-extras/ai-assist`**. Batch in, `number[][]` out, `Result`-wrapped, descriptor-driven. **This is also the Ollama answer** — point it at `http://localhost:11434/v1`; there is no separate Ollama-native embedding API (the `@fgv/ts-extras-ollama` native `embed` was cut — see OQ-1).
  - One-line mental model: **`@fgv/ts-extras-transformers` = the weights run in *your* process; `callProviderEmbedding` = the weights run on *a server you `fetch`*.** Same local-vs-distant split as completion.
- **Embedding text via a cloud or self-hosted provider (OpenAI / Gemini / Ollama / openai-compat / Mistral)?** → `AiAssist.callProviderEmbedding({ descriptor, apiKey, params: { input, dimensions?, taskType? }, modelOverride?, endpoint? })` from `@fgv/ts-extras/ai-assist`; `callProxiedEmbedding(proxyUrl, ...)` to route through a backend proxy. `input` is `string | string[]`; the result's `vectors[i]` aligns to `input[i]`. Pass `dimensions` (honored by OpenAI `text-embedding-3-*` and Gemini) and/or `taskType` (Gemini retrieval asymmetry, e.g. `'retrieval-query'` vs `'retrieval-document'`) — both are a **logged no-op** on providers/models that don't support them, never a failure, so a cross-provider call site passes them once. Self-hosted (`'ollama'`/`'openai-compat'`) needs an explicit `modelOverride` (no default embedding model). xAI / Anthropic have no embeddings endpoint and reject up front. **Don't reach for `@fgv/ts-extras-transformers` for this** — that's the in-process path; this is the distant-HTTP path (see the three-way decision shortcut above).
- **Calling a self-hosted Ollama or OpenAI-compatible model?** → Use the `'ollama'` or `'openai-compat'` provider descriptor from `AiAssist.getProviderDescriptor`. Both are `needsSecret: false` — pass `apiKey: ''` and the library omits the `Authorization` header automatically. The `'ollama'` descriptor defaults to `http://localhost:11434/v1`; `'openai-compat'` has `baseUrl: ''` and requires an explicit `endpoint`. **`defaultModel` is `''` for both** — always supply `model` explicitly (e.g. `model: 'llama3.2'`). Pass `endpoint` to override `baseUrl` per call for `callProviderCompletion`, `callProviderCompletionStream`, and `callProviderListModels`. (`executeClientToolTurn` gains the same `endpoint` override once PR #466 merges; until then the tools path uses `descriptor.baseUrl` only.) **Browser CORS:** Ollama only allows requests from `localhost` by default; set `OLLAMA_ORIGINS=*` (or a specific origin) in the Ollama server environment before starting it, otherwise browser calls will be blocked by the CORS preflight.
- **Storing agent memory / a knowledge vault (records, dedup, attributed edges, backlink index)?** → `FileTreeMemoryStore` from `@fgv/ts-agent-memory`. Don't hand-roll a record store, content-hash dedup, or backlink index.
- **Semantic recall over that vault — record-granular vs sub-document?** → **Record-granular** (one vector per record; "which record matches"): wire the store's `vectorIndex` + `embed` and query via `SemanticRetriever`; the index is `InMemoryCosineIndex` (ephemeral) or `SqliteVecVectorIndex` (persistent). **Sub-document / fragment-granular** (many spans per record; "which record AND which `[start,end)` span matches" — the discovery half of search-then-read): wire the store's `fragmentIndex` + `fragmentEmbedder` and query via `FragmentSemanticRetriever` (returns per-fragment `{ target, score, locator?, fragmentId? }` hits, NOT records; supports a `maxPerRecord` cap); the index is `InMemoryFragmentCosineIndex` (ephemeral) or `SqliteVecFragmentIndex` (persistent). A fragment carries at least one of `locator` (advisory span — not a reproduction guarantee) / `fragmentId` (opaque, never parsed); **do not branch on which one is present to decide what kind of hit you have — you know that from the index you queried.** The two paths are independent — wire either, both, or neither. **Don't hand-roll a cosine index, a fragment locator scheme, or a re-embed-on-open loop.**
- **Vector/fragment embeddings must survive a process restart (no re-embed on open)?** → back the store with `SqliteVecVectorIndex` / `SqliteVecFragmentIndex` from `@fgv/ts-agent-memory-sqlite-vec` (BYO `better-sqlite3` `Database`) instead of the in-memory indexes; skip the `rebuild(asRecordSource())` on open. Node-only.
- **Need to measure a `FileTreeMemoryStore`'s resident-memory / open-cost behavior (not change it)?** → wrap the shipped `MemoryIndex` in a counting/timing delegating decorator and pass it as `FileTreeMemoryStore.create({ ..., index })`. It's an instrumentation seam, not a resident-memory fix — every conforming `IMemoryIndex` still materializes whole record bodies; only a faithful delegating decorator is safe (a reshaping index changes write semantics, not just reads).
- **Fetching a URL you do not fully control (server-side)?** → `saferFetchJson` / `saferFetchText` / `saferFetchBytes` from **`@fgv/ts-extras/safer-fetch`**, with `addressGuard: blockPrivateNetworks()` (the option is **required** — omitting it is a compile error, which is the point). Add `responseHeadersGuard: allowContentTypes([...])` to reject on the header rather than after a body transfer, `redirectPolicy: 'validate-each-hop'` when ingesting real-world URLs (every hop is fully address-guarded before any connection, and credential stripping is monotonic), and `retry: { attempts: n }` when you want retry — it is off by default, consumes the overall deadline rather than resetting it, and re-runs the guard from hop 0 on every attempt. For a local sidecar, name every deviation: `blockPrivateNetworks({ allowLoopback: true, allowInsecureHttp: true, allowHosts: ['localhost'], allowPorts: [11434] })`. **Do not hand-roll a timeout + size cap + redirect loop, and do not echo `FetchFailureReason` to an untrusted caller — it is an internal-network scanning oracle.** DNS rebinding remains a documented open limit; a strict `allowHosts` list is the recommended mitigation.
- **Fetching a URL from a browser?** → `SaferFetch.browserSaferFetchJson` (and siblings) from **`@fgv/ts-web-extras`**, with `addressGuard: allowAnyAddress()` — the honest posture, named at the call site. The shared core's deadlines, size cap, content-type gate, taxonomy and retry all apply; the resolved-address guard and per-hop redirect revalidation **do not and cannot**, and `'validate-each-hop'` is refused up front rather than degraded. Read the guarantee table in either README before relying on it.
- **Parsing / comparing language tags?** → `@fgv/ts-bcp47`.
- **Context-conditional resources?** → `@fgv/ts-res`.
- **Authoring, versioning, or resolving LLM prompts that need to vary on context (tenant / language / tone / region) or compose partial fragments?** → `PromptLibrary.create` from `@fgv/ts-prompt-assist`. One YAML file per `(scope, prompt-id)` carries the descriptor + ts-res-conditional candidates; scope-level `_bindings.yaml` supplies slot bindings; root-level `_qualifiers.yaml` (optional) carries the qualifier config. `PromptLibrary.resolve` chain-walks scopes, runs ts-res candidate selection, merges bindings, renders via Mustache with `escape: 'none'`, and returns body + full `IPromptResolveTrace`. **Do not roll your own LLM-prompt loader / renderer; the verbatim Mustache + double-brace rejection are load-bearing.**
- **Binding a prompt slot to the body of another prompt?** → Author a `SlotBinding` with `kind: 'resource', resourceId: '<inner-prompt-id>'` in `_bindings.yaml` or as the slot's `defaultBinding`. `PromptLibrary` resolves the inner prompt recursively (depth-capped via `IPromptLibraryCreateParams.resourceBindingDepthLimit`, default 5; cycle-detected via RFC 8785 canonical-JSON keys) and substitutes the inner body into the outer slot. The full inner trace surfaces in `trace.resourceBindingResolutions[].innerTrace`.
- **Composing one prompt from several resolved prompts (horizontal / multi-contributor composition)?** → Use **`HorizontalComposer`** from `@fgv/ts-prompt-assist` — the safety-closed, first-class composer. Resolve each contributor independently via `PromptLibrary.resolve`, then `HorizontalComposer.create({ contributors, logicalSlots, composedDescriptor, composedBody, safetyPolicy? }).onSuccess((c) => c.compose())`. Each **`IContributorSpec`** pairs a resolved prompt with a composer-layer **`provenance: number`** (provenance is orthogonal to ts-res qualifier selection — contributors are already fully resolved). **`ILogicalSlotConfig[]`** (code-authored at v0.1 — no YAML converter yet) declares the composed prompt's logical-slot space: each carries a `logicalSlotName`, an **explicit `contributorSlots` map** (`{ contributorProvenance, slotName }[]` — name-matching is never implicit; every reference is checked at `create()` against the contributor's `IResolvedPrompt.slots`), a `strategy` (**`LogicalSlotStrategy = 'concatenate' | 'overwrite'`**), and an optional `separator` (default `'\n\n'`). **Directive-aware merge (load-bearing):** per logical slot, contributions are ordered by **ascending provenance** (declared `contributorSlots` order is a stable tiebreaker); **`constraint`-directive contributions are always concatenated first and NEVER dropped, regardless of strategy**; non-constraints then apply the declared strategy on top (`concatenate` joins all ascending with the separator; `overwrite` keeps only the highest-provenance non-constraint). `create()` does synchronous build-time map validation (unique provenance; every referenced contributor + slot exists). `compose()` runs the **directive-aware merge → `applySafeguards` over the merged slot map against the `composedDescriptor`** (per-logical-slot `maxLength` / `allowedDirectives`; reject → `Result.fail`, warn/info → `IComposedPrompt.safeguardFindings`) **→ Mustache render** of `composedBody` (`escape: 'none'`). Returns **`IComposedPrompt`** (`body` + `mergedSlots: ReadonlyMap<SlotName, IResolvedPromptSlot>` + `provenanceTrace: ReadonlyMap<SlotName, ISlotProvenanceEntry[]>` + `safeguardFindings`). This closes the interim safety gap of the consumer-side external-composer path (which reads `IResolvedPrompt.slots` directly and must self-screen). **`IResolvedPrompt.slots`** remains the supported per-slot read surface for callers who want the resolved values without the full composer; the logical-slot processing order is **not** semantically binding (declared order is a tiebreaker for topo-equal slots — a future dependency topo-sort phase may reorder without a breaking change). **Do not hand-roll an external composer or concatenate rendered bodies — use `HorizontalComposer`.**
- **Observing every prompt resolution as it flows (audit / debug / "where did this body come from" / per-tenant traces / offline analysis)?** → Pass `observers?: ReadonlyArray<IPromptObserver>` to `PromptLibrary.create({ ..., observers })` from `@fgv/ts-prompt-assist`. The library fans out at the three public boundaries (`resolve` / `resolveJsonOutput` / `resolveFreeTextOutput`); never fires for nested resource-binding resolves (those roll up under the outer record's `trace.resourceBindingResolutions[].innerTrace`). For the default in-memory store, use **`PromptObservationStore.create({ maxRecords?, qualifierResolver? })`** — implements `IPromptObserver` and exposes a schema-aware `query(criteria)` (by `promptId` / `scope` / `qualifiers` / `outputKind` / `outcome` / `phase` / safeguard disposition / `seq` + `timestamp` range). For high-latency observers (writing to SIEM / remote store), set `fireAndForget: true` on the observer to dispatch without extending `resolve()` latency; default is awaited so the record lands before return. **Observer errors never affect `resolve()`** — failed `Result`, throw, or rejection is swallowed and logged to the injected `logger` at warn. **The default store is most-permissive** (stores `body` / `rawOutput` / `substitutions` verbatim) — redaction + retention are deployment policy: wrap the store with a redacting `IPromptObserver` or substitute it entirely. `seq` + `timestamp` are library-assigned (consistent across every observer); output records cross-link to their resolve record via `linkedResolveSeq`. **`qualifiers` matching is delegated to an injectable `IQualifierResolver`** — default is string equality on supplied axes (deliberately narrower than `PromptLibrary.resolve`'s ts-res match); inject `IQualifierResolver` for similarity-aware semantics. **Do not roll your own prompt-observation ring** — use `PromptObservationStore`, and for non-prompt retain-and-page surfaces use `RetainingRingBuffer` from `@fgv/ts-utils`.
- **Validating a JSON-shaped LLM response against a typed `Converter<T>` + validator chain?** → `PromptLibrary.resolveJsonOutput<K>(req, rawOutput, expectedKind)` from `@fgv/ts-prompt-assist`. Build a `PromptRegistry<TResponse>` where `TResponse` is the consumer's response union (each member carries a `kind: '<discriminator>'` field). Register Converters via `registry.converters.register(id, kind, converter)` and validators via `registry.outputValidations.register(id, { appliesTo, validate })`. Caller passes `expectedKind` as a string literal (`'cited'`, `'classifier'`, etc.); `K` is inferred and the return type narrows to `Extract<TResponse, { kind: K }>` automatically. At the public-API entry, `resolveJsonOutput` runtime-verifies that the descriptor's `output.kind === 'json'` AND that `descriptor.output.converterId` is registered to produce `expectedKind` — a mismatch (caller asked for `'cited'` but the descriptor's converter produces `'classifier'`) rejects loudly with the prompt id + actual-vs-expected kinds, *before* the pipeline runs. After the entry check passes, the pipeline strips Markdown fences (via `AiAssist.fencedStringifiedJson`), `JSON.parse`s, dispatches to the Converter recorded under `(id, kind)` (no cast between the Converter type and validator inputs), then chains the validators (each narrowed by `value.kind ∈ appliesTo`). Loader-side checks reject incompatible descriptors at `describe()` / `resolve()` time (belt); the runtime path re-checks `value.kind` per validator (suspenders). The combined entry-check + belt + suspenders pin every degree of caller-asserted-`T` freedom that the previous `resolveAndValidateOutput<T>` API exposed — there is no longer a path where the return type's runtime kind diverges from what the descriptor declared. **Free-text output:** for descriptors whose `output.kind` is `'free-text'`, use `resolveFreeTextOutput(req, rawOutput)` — it runtime-verifies the descriptor's output kind and returns the raw output verbatim as `Result<string>`. No `TResponse` involvement; no Converter; no caller assertion.
- **Enforcing safety policies (length cap, pluggable value screeners, anti-jailbreak preface) on a resolved prompt?** → `IPromptLibraryCreateParams.safetyPolicy` from `@fgv/ts-prompt-assist`. Carries `defaultMaxLength`, `screeners` (ordered `IScreener[]`; each `screen(ctx)` is async and returns `Result<ISafeguardFinding[]>`), and `antiJailbreakPreface` (consumer-supplied post-render framing — library ships no default content). Use `createPatternScreener({ patterns, onMatch, screenedSources? })` for regex injection screening (`lastIndex` reset between values; `screenedSources` is the screener-owned source allowlist). Screeners run sequentially; the first `disposition: 'reject'` finding (or a screener `fail()`) fails the resolve and short-circuits the rest. Warn / info findings (screener findings under `'warn'` / `'info'`, plus `'enforced-override-ignored'` from the merge) surface in `trace.safeguardFindings`; reject paths (length-cap violations, reject findings, screener `fail()`s) fail the resolve with the rejection in the error message rather than on a trace. Findings carry open `kind`s, optional `metadata`, and `screener` attribution. Implement `IScreener` directly for ML-classifier or remote-call screeners.
- **Mustache rendering for LLM prompts (verbatim, no HTML escaping)?** → `MustacheTemplate.create(template, { escape: 'none' })` from `@fgv/ts-extras` (mustache packlet). The template string is the first argument; the options bag is second. Uses a per-instance `Mustache.Writer` — no mutation of the global `Mustache.escape`, so concurrent renderers with different escape strategies coexist. Default `'html'` preserves the existing back-compat behaviour; pass a `(value) => string` callback for a custom strategy. `@fgv/ts-prompt-assist` consumes the `'none'` strategy internally.
