# Result: `ts-utils-async-detailed-result`

**Branch:** `ts-utils-async-detailed-result` (from `release` @ `b85b094b7`)

## Summary

Chaining an async step off a `DetailedResult<T, TD>` silently degraded it to a plain `Result<T>`
and lost `TD`. `DetailedSuccess`/`DetailedFailure` extend `Success`/`Failure` and never declared
`thenOnSuccess`/`thenOnFailure`, so they inherited `thenOnSuccess<TN>(cb): AsyncResult<TN>` — a
signature with no detail type parameter and nothing detail-shaped to return. This closes the gap
with `AsyncDetailedResult<T, TD>`, which **extends `AsyncResult<T>`** (forced, not stylistic — see
OQ-1), plus overrides on both detailed classes. The plain-`Result` path is untouched: the API
report diff is **purely additive, with zero removed or modified lines**. `safer-fetch` is the first
real consumer, and its pass was measured rather than asserted — 3 of 21 checks converted, which is
the honest minority the brief anticipated.

## The type-level assertion, and proof it fails against the old code

The brief required a type-level test because **this bug type-checked** — every runtime assertion in
the new suite would have passed against the broken code.

`asyncDetailedResult.test.ts` asserts with the conditional-type identity trick:

```ts
type Equals<X, Y> = (<T>() => T extends X ? 1 : 2) extends <T>() => T extends Y ? 1 : 2 ? true : false;
```

Mutual `extends` would **not** have worked: `DetailedResult<T, TD>` *is* assignable to `Result<T>`,
so a bivariant check passes against the very bug under test. Five chains are pinned, including a
negative control asserting the plain path still yields exactly `Result<number>`.

**Verified, not assumed.** I disabled only the four overrides (leaving `AsyncDetailedResult`
defined) and rebuilt. The build failed with 20+ errors in the test file, the load-bearing ones being:

```
TS2741: Property '_detailed' is missing in type 'AsyncResult<number>'
        but required in type 'AsyncDetailedResult<number, Reason>'.
TS2339: Property 'detail' does not exist on type 'Failure<number>'.
```

That is the silent bug, made loud. The overrides were then restored and the build re-verified green.

### The split, which is the actual finding

Of the 21 checks, only **7** are on an awaited `DetailedResult` — the only population the ts-utils
gap could ever have blocked. **3 converted.** The rest:

| Site | Why it stays |
|---|---|
| `_walk` ×3 (`guarded`, `cleared`, `attempted`) | hop-loop **control flow** — the `CODING_STANDARDS` exemption, upheld by S3's own reviewer. Two also carry a `logger.detail` side effect. |
| `_runAttempt` (`walked`) | retry branch, not a chain: it reads `walked.detail` to decide whether to **recurse** after a delay. |
| 14 remaining | on synchronous results, or on plain `Result`s that never carried a detail. The new surface does not reach them. |

`_execute`'s `parsed` check is the one genuine judgement call: it is a sync `Outcome` followed by an
async step, so it *could* chain — but the `DeadlineWatch` is created between the check and the async
call and disposed after it, and chaining would push construction into a callback where the trailing
`watch.dispose()` cannot see it. Converting would trade a readability loss for a metric. Left, per
OQ-3.

**Conclusion: the ts-utils gap explained a minority of this file's imperative checks, and most of
`saferFetch.ts` legitimately stays imperative.** The brief named this as a legitimate outcome and it
is the outcome. The most informative number is the last row of the table: `_propagate` — a helper
that exists *only* to re-type a failure across a stage boundary because the detail could not
propagate through a chain — lost 3 of its 11 call sites.

The brief's own rough estimate ("~3 of those 22 are on awaited values") landed on the right
conversion count for the wrong reason: **7** are on awaited values; **3** survive the exemptions.

## Open questions, as resolved

**OQ-1 — the shape. Took the recommendation (a), and found it was forced rather than preferred.**
An override's return type must be assignable to the base method's. `DetailedSuccess.onSuccess` can
return `DetailedResult<TN, TD>` only *because* `DetailedSuccess extends Success`. The async override
needs the identical property, so `AsyncDetailedResult<T, TD>` **must** extend `AsyncResult<T>` — a
standalone sibling could not have been returned from an override at all.

The brief's escalation trigger (a contravariant position → prefer option (c)) **did fire**, but only
on the **static** side: a static `from` narrowing its parameter from `Result` to `DetailedResult` is
unsound, since it is reachable through `AsyncResult`'s static type. Renaming it `fromDetailed`
costs nothing and the inherited `from` still works. The instance surface was clean and compiled on
the first attempt, so option (c) was not needed.

**OQ-2 — build the ladder, exactly as far as `AsyncResult` already goes.** All eight existing
methods, no new combinators. Deliberately **no `captureAsyncDetailedResult`**: a captured throw
supplies no detail, so it would differ from `captureAsyncResult` only in return type.

**OQ-3 — did not force the `safer-fetch` pass.** See the measured split above. This is the
"escalate if the honest answer is *most of it should stay imperative*" case, and that is the honest
answer.

## Design decision worth flagging: rejections carry no detail

A callback that throws synchronously or rejects becomes a `DetailedFailure` with
`detail: undefined`, never an escaped exception.

The acceptance criterion read "become a `Failure` **carrying the detail**". I read that as "stays in
the detailed family and never escapes", because `undefined` is the only honest detail available: the
thrown error supplies no `TD`, and carrying the *upstream* detail forward would pair this failure's
message with a previous operation's detail — on the success path it would additionally promote a
**success** detail onto a failure. This matches `async-result-family-design.md` § 6 exactly, where
`mapDetailedResultsAsync` was given the same treatment for the same reason. Flagging the reading in
case the criterion intended something stronger; if so, the change is localized and cheap.

## Observability self-audit

- **No `console.*` added anywhere.** The new ts-utils code emits no diagnostics at all, which is
  correct for a `Result` primitive — it is *plumbing for* diagnostics, not a source of them.
- `AsyncDetailedResult.report()` preserves the full `IResultReporter` integration and, on the
  failure arm, passes the **detail** through to `reportFailure(level, message, detail)` — a
  capability the plain `AsyncResult.report` cannot offer. Covered by test.
- `aggregateError` forwards an `ErrorFormatter<TD>` so an aggregated message can name the detail
  (`[network] bad`). Covered by test.
- No observability was lost in `saferFetch.ts`: both `resolved.logger.detail(...)` sites live in
  `_walk`, which was not converted. No log call moved, was added, or was dropped.
- No secrets or response bodies enter any new message. The one new value that can reach a message is
  `_errorMessage(err)` from a thrown callback, which was already the plain path's behavior.

## Other-package consumers found losing detail

**None** — and this is a verified negative, not an unchecked box. Full write-up in
`findings/inbox/2026-08-06-no-other-consumer-loses-detail.md`.

All 34 `thenOnSuccess`/`thenOnFailure` call sites outside `ts-utils` were enumerated; **not one is
on a `DetailedResult`**. The five out-of-scope consumer packages (`ts-json`, `ts-res`,
`ts-json-base`, `ts-utils-jest`, `ts-web-extras`) do not use the async bridge at all. The three
heaviest bridge users (`ts-agent-memory` 23 sites, `ts-prompt-assist` 4, `tools/ks` 1) never
reference `DetailedResult`. Independently corroborated by the full-monorepo build producing no
API-report change outside `ts-utils`.

The trap was armed and only `safer-fetch` had walked into it — consistent with `safer-fetch` being
the package that surfaced it, since a consumer whose taxonomy *is* its product is the one that
notices. **This fix is preventive, not remedial.**

Per the brief, **no other consumer package was migrated.**
