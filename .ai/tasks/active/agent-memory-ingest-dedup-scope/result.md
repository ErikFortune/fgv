## Summary

`@fgv/ts-agent-memory` had two dedup layers that disagreed: the store honored each kind's declared
`dedupScope`, while the ingest orchestrator's stage-4 layer-1 exact match ignored it entirely and
always behaved as `'content'` — `dedupScope` had zero references anywhere in `ingest/`. The reported
fix was not expressible through the existing seam, because the orchestrator holds an `IMemoryStore`
and the write policies were private to `FileTreeMemoryStore`; so this stream first added a narrow
read accessor (`IMemoryStore.dedupScopeFor(kind)`) that resolves the same chain the store applies,
then made layer-1 read through it and refactored both pre-existing store read sites onto it, leaving
exactly one declaration site. Independently, it fixed the second-order hazard the reporter identified
— a `duplicate-of` collapse removed an address that sibling edges in the same pass were built
against, failing the *whole* ingest item — by redirecting such edges onto the record the candidate
collapsed into, which fixes `'content'` kinds too, where the collapse is correct but the ingest still
should not fail. Shipped alongside: the `LIBRARY_CAPABILITIES` correction (all three listed
fast-follows ship, not the two the brief named) and `.claude/project/agent-memory-ingest-design.md`,
the note three source files have cited since the packlet shipped but which never existed.

## Sibling sweep on the new seam

**Siblings considered:** the other `IMemoryStore` members (`get` / `getById` / `list` / `listScoped` /
`asRecordSource` / `put` / `delete`) and the `IMemoryIndex` injection seam.

**Asymmetry found, and deliberate:** every other `IMemoryStore` member returns
`Promise<Result<...>>`; `dedupScopeFor` returns a bare `DedupScope`. This is a considered divergence,
not an oversight:

- Those members perform I/O against the FileTree or the derived index and have real failure modes.
  `dedupScopeFor` reads constructor-injected configuration, touches nothing, and **cannot fail** —
  every link in its chain (`_writePolicies.get(kind) ?? _defaultPolicy`, then
  `policy.dedupScope ?? DEFAULT_DEDUP_SCOPE`) has a total default.
- Wrapping a total, synchronous config read in `Promise<Result<>>` would force the caller to `await`
  inside a synchronous `Array.filter` predicate — the exact call site that needs it — restructuring
  `_findExactMatch` around a failure that cannot occur.
- `asRecordSource()` is the precedent: it is already a synchronous, non-`Result` member of the same
  interface, for the same reason (it returns an adapter, performs no I/O, cannot fail).

**`IMemoryIndex` comparison:** that seam is an *injection* point — the store calls into a
consumer-supplied implementation, and its create-param doc carries a long warning that a reshaping
index changes write semantics. `dedupScopeFor` is the opposite direction: a *read* the store exposes
about its own already-injected configuration. It cannot be reshaped by a consumer of the store, and
it deliberately surfaces only the scope value rather than the `IWritePolicy`, so it cannot become a
back door for invoking `admit` or `applyUpdate` out of band. No divergence to reconcile.

**Naming:** `dedupScopeFor(kind)` follows the existing internal `_policyFor(kind)` /
`_codecFor(kind)` convention.

## What behavior changed for existing hosts (OQ-3)

**Changed, intentionally, with no opt-in flag.** For a kind whose effective `dedupScope` is
`'entity'`, ingest layer-1 no longer collapses two *distinct* entities that share a byte-identical
body. Candidates that previously came back `deduped` now come back `written`, and the records
genuinely persist. Hosts that were silently losing turns whose summaries happened to match will stop
losing them — the vault gains records it should always have had.

**Precisely who is affected:**

| Kind's policy | Effective scope | Ingest behavior |
|---|---|---|
| `MemoryCapCullPolicy` (experience) | `'entity'` | **changed** — no longer collapses distinct entities |
| `TemporalVersionedPolicy` (versioned) | `'entity'` | **changed** — same |
| custom policy declaring `'entity'`, or declaring nothing (→ `DEFAULT_DEDUP_SCOPE`) | `'entity'` | **changed** — same |
| `KnowledgeLwwPolicy` | `'content'` | unchanged |
| **no registered policy** | `'content'` | **unchanged** — see below |

The last row corrects the brief. `DEFAULT_DEDUP_SCOPE` is `'entity'`, but it is only reached when a
policy object exists and declares no `dedupScope`. A kind with no registered policy falls back to the
store's *default policy*, which is a `KnowledgeLwwPolicy` — and that declares `'content'` explicitly.
So unpoliced kinds were `'content'` on both paths before this change and remain so; the two paths
were already in agreement there. The brief's "every experience and versioned kind" is right for hosts
that register the experience policies (the documented way to get experience semantics), but overstated
for hosts that registered nothing.

**The identity codec sharpens this further.** Whether an `'entity'` kind was ever exposed depends on
whether its codec puts distinct entities in the *same* scope, because the exact-match cohort was
always scope-filtered:

| Codec | Address shape | Distinct entities share a scope? | Was it exposed? |
|---|---|---|---|
| `MtmIdentityCodec` | `conversations/<conv>` + `turn-<n>` | **yes** | **yes** — the reporter's shape |
| `LtmIdentityCodec` | `conversations` + `<convId>` | **yes** | **yes** |
| `KnowledgeIdentityCodec` | `knowledge` + `<docId>` | yes | n/a (`'content'` by policy) |
| `TemporalIdentityCodec` | `<base>/entities/<id>` + `<id>` | **no** — one scope per entity | **no** |

So the bug bit **flat** `'entity'` kinds — MTM turns and LTM conversations — and never temporal ones,
which the per-entity scope already isolated. Within a single temporal entity's scope every version
shares the same resolved `idStem`, so the new entity narrowing is a no-op there and the pre-existing
"skip invalidated versions" filter continues to do the real work. Both facts are pinned by tests
(`the reporter's literal shape: two MTM turns in ONE conversation scope`, and
`a TEMPORAL entity kind keeps distinct entities apart (scope isolation, unchanged)` — the latter
deliberately passes with and without the fix, as a guard against someone later assuming the
narrowing is what protects temporal kinds).

Also changed, independent of `dedupScope` and affecting **every** ingest host including `'content'`
ones: a `duplicate-of` collapse no longer fails the whole ingest item when a sibling edge was built
against the collapsed candidate. Strictly a widening — ingests that used to fail now succeed; none
that used to succeed now fail. The one preserved failure is an edge *sourced* at a collapsed
candidate, which remains a loud rejection by design.

**Not flagged, on purpose.** A flag would preserve the very disagreement that is the defect. The
change is called out in the change file, in the README under an explicit warning heading, in the
`LIBRARY_CAPABILITIES` entry, in the commit message, and in the PR body.

**Downstream:** `@fgv/ts-agent-memory-sqlite-vec` builds untouched — it implements `IVectorIndex` /
`IFragmentVectorIndex`, not the store seam, so the brief's escalation tripwire did not fire. This
confirms the accessor landed on the right interface.

**External `IMemoryStore` implementers** face a compile break (a new required member). Correct and
unshimmed per `ACTIVE_DEVELOPMENT.md`, which puts all of `ts-agent-memory` on the active surface.

## Open questions

- **OQ-1 (accessor shape)** → narrow `dedupScopeFor(kind): DedupScope`. It answers exactly the
  question the orchestrator has, keeps `IWritePolicy`'s mutation surface out of a read seam, and
  cannot become a back door into admission logic. No escalation needed.
- **OQ-2 (emit `duplicate-of` for a same-id identical-body candidate)** → yes, still emitted, and
  landed in the same commit as the redirect, never before it. Pinned by a test.
- **OQ-3 (keep `'entity'` as the default)** → default kept, behavior fixed, called out loudly rather
  than softened into a flag. See the section above, including the one correction to the brief's
  blast-radius framing.

**Still open (recorded to `findings/inbox/`, not fixed here):**

- Collapsed candidates are never offered to the `IRelationExtractor`, so a host cannot propose the
  semantically correct `A → R` edge for a collapsed `B`. The redirect closes the reported hazard
  completely; making collapsed candidates *visible* raises a genuine write-semantics question (may a
  `duplicate-of` collapse mutate the target record's links?) that deserves its own scoping. No known
  consumer impact.
- `CODING_STANDARDS.md` has no "Docs ship with the code" section, though briefs cite it. Either add
  it or drop the citation from the brief template.

## Deviations from the brief

1. **The accessor went on `IMemoryStore` where it actually lives** — `store/fileTreeMemoryStore.ts:110`
   — not in `types/memoryStore.ts`, which **does not exist**. Not treated as a missing-input STOP: the
   rule governs required-reading *files* that can't be read, and here the seam was fully readable, just
   co-located with its implementation. Extracting the interface into a new file would move a `@public`
   declaration between packlets and churn imports across `ingest/`, `tools/`, and the test suite —
   out-of-scope refactoring with no bearing on the defect. Recorded in `findings/inbox/`; the ledger
   entry's package surface was corrected to match.
2. **Deliverable 4 was larger than the brief's reading.** The brief named two stale fast-follows;
   verification found all three stale (the temporal versioned write path + temporal retrievers ship
   too). Because the brief said to verify rather than trust, all three were corrected and the
   fast-follows list removed entirely. Substantive L2/L3 capability paragraphs were added, since both
   were previously documented only as pending.
3. **One brief factual correction**, folded into the deliverables rather than merely reported: the
   effective default scope for an unpoliced kind is `'content'` via `KnowledgeLwwPolicy`, not
   `DEFAULT_DEDUP_SCOPE`. Documented in the design note §1, the README, the capabilities entry, and
   the change file, and pinned by a test.

Nothing in the brief's out-of-scope list was touched: no `ts-extras` / `ts-web-extras` /
`samples/testbed` (owned by `safer-fetch-s3`), no `ts-agent-memory-sqlite-vec`, no other
`libraries/*`. Both shared files were edited section-locally with no surrounding reflow.
